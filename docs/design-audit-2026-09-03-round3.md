## 먼저 알아야 할 것

**시즌의 실패 엔딩에 도달할 수 없습니다.** `SYSTEM COLLAPSE`는 압박 82 이상 또는 사람 피해
70 이상일 때 나오는데, 마지막 사건을 4,000회 무작위로 완주시킨 결과 압박 최대치는 33,
사람 피해 최대치는 31이었습니다. 케이스마다 자원이 `initialResources`로 초기화되는데 엔딩
임계값은 시즌 누적을 전제로 쓰여 있습니다. 9개 엔딩 중 2개가 구조적으로 닫혀 있고,
그중 하나가 유일한 실패 엔딩입니다.

그 다음은 장면 안에서 절대 고를 이유가 없는 선택지 11개이고, 세 번째는 2차에서 고친 확정
콘솔이 선택지 카드를 덮는 문제입니다.

P-2(번들·CSS 분할)는 두 번째 측정까지 마치고 닫았습니다. 근거는 이 문서 마지막에 있습니다.

## 엔딩 (E · 3건)

### E-1 【높음】 실패 엔딩이 도달 불가능합니다

`getEndingVariant`의 첫 분기입니다.

```
if (pressure >= 82 || humanCost >= 70) return SYSTEM COLLAPSE

마지막 사건 4,000회 무작위 완주 (자원은 케이스 시작마다 초기화)
  최대 압박      33   (필요 82)
  최대 사람 피해 31   (필요 70)
```

케이스는 9~12회 판단이고 시작 자원은 매번 같습니다. 한 케이스 안에서 압박을 82까지
올리려면 시간·현금·피로·사람 피해가 동시에 무너져야 하는데, 그만한 폭의 효과가 없습니다.
"권한은 있었지만 감당할 시간이 남지 않았다"는 결말은 쓰여 있고 화면도 있지만 아무도 보지
못합니다.

**고칠 곳** — 임계값을 마지막 사건의 실제 분포에 맞추거나(압박 30·사람 피해 25 부근),
엔딩 판정에 시즌 누적치를 넘기십시오. `caseResults`에 케이스별 최종 자원이 이미 있으므로
누적 최댓값을 계산할 수 있습니다. 후자가 원래 의도에 가깝습니다.

### E-2 【중】 FIELD PACT도 한 번도 나오지 않습니다

`trust >= 65 && legitimacy < 45` 조건인데, 마지막 사건에서 믿음을 올리는 선택은 공정함도
같이 올립니다. 4,000회 중 0회입니다.

**고칠 곳** — 마지막 사건에 믿음을 올리면서 공정함을 깎는 선택지를 넣거나(현장과의 사적
합의), 조건을 `trust - legitimacy >= 20`처럼 상대값으로 바꾸십시오.

### E-3 【중】 엔딩 절반이 두 개에 몰립니다

```
4,000회 무작위 완주의 엔딩 분포
  OPEN QUESTION       26.2%    OPEN OVERSIGHT      26.0%
  EVIDENCE REFORM     16.0%    QUIET COVER         11.6%
  HUMAN RECORD        10.8%    COLD JUSTICE         6.0%
  PROFITABLE SILENCE   3.4%    SYSTEM COLLAPSE / FIELD PACT  0%
```

`OPEN QUESTION`은 아무 조건에도 걸리지 않았을 때의 기본값입니다. 네 번 중 한 번이 "해당
없음"으로 끝난다는 뜻입니다.

**고칠 곳** — 기본값에 도달하는 경로를 줄이는 쪽이 아니라, 기본값 자체를 마지막 자원 배치를
읽어 쓰는 결말로 만드십시오. 지금은 조건 사다리의 낙오 지점입니다.

## 데이터 (D · 2건)

### D-1 【중】 장면 안에서 지배당하는 선택지가 11개 있습니다

같은 장면의 다른 선택지보다 여섯 자원 전부에서 같거나 나쁘고, 하나 이상에서 나쁩니다.
숫자를 보는 플레이어에게는 고를 이유가 없는 칸입니다.

```
c2_meeting_shadow   {time:-12, legitimacy:-4, fatigue:4}
  ← c2_meeting_meet {time:-10, trust:10, legitimacy:-2, fatigue:2} 이 모든 축에서 우위

f_start_map         {time:-10, legitimacy:3, humanCost:2, fatigue:4}
  ← f_start_expose  {trust:4, legitimacy:6, humanCost:-2, fatigue:3}

c5_start_stop_signature {humanCost:-6, trust:5, capital:-8, fatigue:4}
  ← c5_start_stop_redesign {capital:-8, trust:6, humanCost:-8, fatigue:4}
```

마지막 것은 2차에서 추가한 오프닝 전용 선택지입니다. 갈래마다 고유한 선택지를 넣으면서
그 갈래의 기존 선택지와 비교하지 않았습니다.

**고칠 곳** — `scripts/check-balance.mjs`에 장면 내 지배 검사를 추가하십시오. 케이스 열
사이의 지배는 이미 검사하고 있으니 같은 함수를 장면 단위로 한 번 더 돌리면 됩니다. 그다음
11개를 하나씩 풀어야 새 선택지를 넣을 때 같은 일이 반복되지 않습니다.

### D-2 【낮음】 오프닝 복제 대사 45줄이 남아 있습니다

319개 고정 선택지 중 고유 대사는 274줄입니다. 남은 45줄은 케이스 오프닝 15개가 기준 장면의
선택지를 그대로 복제한 부분입니다. 같은 판단이므로 같은 대사인 것이 맞지만, 세 갈래를
연속으로 보는 재플레이에서는 도입부만 다른 같은 말로 읽힙니다.

**고칠 곳** — 급하지 않습니다. 2차에서 넣은 갈래 전용 선택지가 이미 차이를 만들고 있고,
나머지 세 줄까지 갈래별로 쓰려면 45줄을 새로 써야 합니다. 다음 대사 작업 때 함께 하십시오.

## UI · UX (U · 2건)

### U-1 【중】 확정 콘솔이 선택지 카드 두 장을 덮습니다

2차에서 확정 버튼을 뷰포트에 고정한 결과, 콘솔이 화면 아래 절반을 차지합니다. 390×844에서
콘솔은 top 480, 높이 356px이고, 그 아래로 선택지 카드 두 장이 들어갑니다 — 방금 고른 카드가
105px, 다른 대안이 238px 가려집니다.

```
콘솔 top 480 · 높이 356 · 뷰포트 844
가려지는 카드  선택한 카드 105px,  다른 선택지 238px
```

"다시 고르기"를 누르기 전에 대안을 비교하려면 스크롤해야 합니다. 확정을 빠르게 만든 대신
비교를 느리게 만들었습니다.

**고칠 곳** — 콘솔이 열릴 때 선택지 목록을 콘솔 위 공간으로 스크롤해 맞추거나(스크롤 대상이
버튼이 아니라 목록이 됩니다), 콘솔을 접힌 상태(요약 한 줄 + 확정/취소)로 열고 상세는 펼치기로
두십시오. 후자가 높이를 356px에서 100px 아래로 줄입니다.

### U-2 【낮음】 콘솔이 열리면 페이지가 491px 늘어납니다

`.game-board.has-commit-console`의 `padding-bottom: 60dvh`가 고정값이라, 실제 콘솔 높이
356px보다 135px 더 늘어납니다. 스크롤 끝에 빈 공간이 생깁니다.

**고칠 곳** — 콘솔 높이를 CSS 변수로 내보내고 패딩을 그 값 + 여백으로 잡거나, 콘솔 상세를
접으면(U-1) 고정값이 실제 높이에 가까워집니다.

## 유지보수 (M · 1건)

### M-1 【중】 AppContent가 여전히 진입 청크의 98KB입니다

소스맵으로 진입 청크의 구성을 실측했습니다.

```
진입 청크 원본 소스 453KB / 47개 파일
   98KB  src/AppContent.jsx        62KB  src/gameData.js
   49KB  src/gameLogic.js          22KB  src/gameDialogue.js
   21KB  src/advancedSystems.js    19KB  src/state/savedState.js
   18KB  src/components/AdaptiveMusic.jsx
```

화면 전용이라 떼어낼 수 있는 큰 덩어리는 없습니다. `AppContent`가 인트로를 그리기 때문에
그 import 그래프 전체가 첫 화면에 필요합니다. 크기 문제 이전에, 2,300줄 한 파일에 상태와
전환이 모두 있다는 것이 이번 세 차례 작업에서 가장 자주 부딪힌 지점이었습니다.

**고칠 곳** — 인트로를 `AppContent`에서 떼어내는 것이 유일한 구조적 해법입니다. 인트로가
읽는 상태(이름, 프로토콜, 출신, 세이브 슬롯, 시즌 진행)는 게임 상태의 일부일 뿐이므로,
그 부분만 별도 훅으로 올리면 `AppContent`는 시작 이후에만 마운트되고 그래프 62KB와
대사 22KB도 함께 뒤로 갑니다. 크지만 이 저장소에서 남은 유일한 큰 정리입니다.

## P-2 종결 기록

1차 감사의 P-2는 두 가지 방법을 제안했습니다. 둘 다 만들어 재봤고, 둘 다 채택하지 않습니다.

**CSS 지연 청크 — 두 번째 측정.** `play.css`를 화면 청크로 옮기면 `index.css`가 155KB →
102KB(gzip 27.5 → 19.0KB)가 됩니다. 1차에서는 `@layer`로 시도해 인트로 계산 스타일 7건이
바뀌었고, 이번에는 레이어 없이 로드 순서만 바꿔 6개 화면(인트로 데스크톱·모바일, 랭킹,
플레이 데스크톱·모바일, 결과)의 모든 요소 계산 스타일을 35개 속성으로 비교했습니다.

```
비파생 속성 차이 101개 (요소, 속성) 형태
  인트로   13개  — .panel-title-row, span, small, h2 가 play.css에 살고 있음
  랭킹     동일 계열
  플레이   49개  — .scene, .game-board, 칩(b/small) 등 result·extensions가
                   play를 덮어쓰던 것이 뒤집힘
```

정리하려면 40여 규칙을 파일 사이로 옮기고, 앞으로 "화면 파일이 오버라이드 레이어보다
뒤에 온다"는 규칙을 영구히 져야 합니다. gzip 8.5KB의 값이 아닙니다. 제대로 하려면 다섯
파일을 순서에 의존하지 않는 하나의 집합으로 평탄화하거나, 화면별 CSS를 만들고 규칙 단위
동등성을 증명하는 빌드 단계가 필요합니다. 둘 다 이 감사의 범위 밖입니다.

**장면 그래프 지연.** 한국어 문자열을 전부 스텁으로 바꾸면 진입 청크가 348KB → 261KB
(gzip 115.7 → 85.2KB)입니다. M-1의 인트로 분리가 선행되지 않으면 한 바이트도 뒤로 갈 수
없습니다. 그래서 이 항목은 M-1에 흡수해 닫습니다.
