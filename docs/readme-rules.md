# README 규칙

README는 이 게임의 **포트폴리오 첫 페이지**입니다. GitHub 주소를 받은 사람이 30초 안에 무슨 게임인지,
어떻게 만들었는지, 어디서 해 볼 수 있는지 알고 떠나야 합니다. 개발자를 위한 자세한 내용은 같은 파일
아래쪽의 접힌 블록(`<details>`)에 둡니다. 다른 문서로 옮기지 않는 까닭은 링크를 한 번 더 누르는 사이에
읽는 사람이 떠나기 때문입니다.

README는 거의 매일 고쳐집니다. 그래서 아래 규칙 가운데 잴 수 있는 것은 `npm run check:readme`
(`scripts/check-readme.mjs`)가 지키고, `verify:static`과 `check:changed`(README, 이 문서, `docs/images/`가 바뀌면)가
그것을 돌립니다.

## 1. 두 부분

| 부분 | 무엇 | 누가 읽나 |
|---|---|---|
| 펼쳐진 부분 | 소개, 캡처, 만든 방식, 해 보기, 만든 이 | 처음 온 사람 |
| 「자세히 보기」 | 주제별 `<details>` 블록 | 궁금해서 펼친 사람 |

## 2. 펼쳐진 부분의 순서 (검사함)

1. 제목(`#`)과 한 줄 소개, 플레이 링크, 언어 링크, 만든 이 한 줄 — 가운데 정렬 머리
2. 큰 캡처 한 장(있으면)
3. `## 어떤 게임인가` — 굵은 첫 구절로 시작하는 짧은 글머리 3~4개
4. `## 화면` — 캡처 2~4장(휴대폰과 PC)
5. `## 우리가 만든 방식` — 숫자가 뜻을 갖는 글머리 4~6개
6. `## 바로 해 보기` — 플레이 주소와 내 PC에서 띄우는 네 줄
7. `## 만든 이` — 크레딧 줄은 글자 그대로 둡니다(STUDIO 찹쌀떡 · Mochi Verse · もちぷよ, CREATOR SUPASONIC & ALICE와 두 메일)
8. `## 라이선스`
9. `## 자세히 보기` — 마지막 절. 이 아래는 `<details>` 블록만

검사는 3, 5, 6, 7, 9의 제목이 이 순서로 있는지, 9가 마지막인지, 첫 `<details>` 뒤에 블록 밖 글이 없는지를 봅니다.
사이에 절을 더하는 것은 됩니다.

## 3. 길이 (검사함)

- 펼쳐진 부분(모든 `<details>` 바깥)은 **12,000바이트**(UTF-8) 이하입니다. 한글로 대략 4,000자, 휴대폰으로
  스크롤 여섯 번쯤입니다. 넘으면 무엇을 블록 안으로 내릴지 고릅니다.
- 펼쳐진 부분에는 `YYYY-MM-DD` 날짜를 쓰지 않습니다. 날짜가 붙은 문장은 작업 기록이고, 작업 기록은 블록
  안이나 `docs/history.md`에 둡니다.

## 4. 표 (검사함)

- 어디서든 **3열 이하**입니다. 넷째 열이 필요하면 표 대신 목록으로 씁니다(`- **이름** — 설명` 아래에 `  - 결과: …`).
- 펼쳐진 부분의 칸은 **40자** 이하, 블록 안의 칸은 **160자** 이하입니다(링크 주소는 세지 않음). 칸이 문장이면
  목록이 휴대폰에서 더 잘 읽힙니다.
- 표는 정말 비교가 필요할 때만 씁니다. 항목 셋 이하라면 글머리로 충분합니다.

## 5. 접힌 블록 (검사함)

```html
<details>
<summary><b>주제</b> — 펼쳐 볼 까닭 한 줄</summary>

(빈 줄 다음부터 마크다운)

</details>
```

- `<summary>`는 한 줄, 보이는 글자 **60자** 이하. 굵은 주제 이름 다음에 「왜 펼쳐 볼 만한지」를 씁니다.
- `</summary>` 다음과 `</details>` 앞에는 빈 줄을 둡니다. 없으면 GitHub가 안쪽 마크다운을 그리지 않습니다.
- 블록 안에 블록을 넣지 않습니다. 블록 안의 제목은 `###`부터 씁니다.
- 블록 하나는 주제 하나입니다. 다른 문서나 스크립트가 「README 「수동 배포와 롤백」」처럼 제목으로 가리키므로,
  블록 안 제목의 이름을 바꿀 때는 `grep -rn "README" docs scripts .github`로 가리키는 곳을 함께 고칩니다.

## 6. 이미지 (검사함)

- `<img src="docs/images/…" alt="…" width="…">`로 씁니다. `![]()`는 폭을 정할 수 없어 쓰지 않습니다.
- 파일은 `docs/images/`에, 한 장 **400KB** 이하. WebP를 먼저 쓰고, 휴대폰 캡처는 `width="260"` 안팎,
  PC 캡처는 `width="720"` 이하로 둡니다.
- `alt`는 화면에 무엇이 보이는지 한 문장으로 씁니다(「게임 화면」이 아니라 「휴대폰에서 카드 다섯 장을 든 테이블」).
- 캡처는 `npm run capture:readme`(`scripts/capture-readme-shots.mjs`)로 다시 찍습니다. 손으로 찍은 그림은 화면이
  바뀌면 낡은 채로 남기 쉽습니다. 화면이 크게 바뀐 날 다시 찍습니다.

## 7. 말투 (사람이 지킴)

- 만든 이는 **우리**입니다. 「저는」, 「만든 사람」이라고 쓰지 않습니다.
- 문장은 짧게. 한 문장에 한 가지. 「~할 수 있습니다」보다 「~합니다」.
- 숫자는 뜻이 있을 때만 씁니다. 「검사 29개」는 「통과한 커밋만 배포」의 근거라서 씁니다. 펼쳐진 부분의
  숫자는 되도록 `check:doc-numbers`가 다시 세는 문장 꼴(「검사 #개를 병렬로」, 「사건 #개」, 「용어집 #개」)로 써서
  낡지 않게 합니다.
- 내부 용어(갈래 이름, PR 번호, 예산 이력, 마이그레이션 수)는 펼쳐진 부분에 쓰지 않습니다.
- 자랑은 결과로 합니다. 「철저한 테스트」 대신 「통과한 커밋만 운영에 나갑니다」.

## 8. 펼쳐진 부분에 넣지 않는 것

작업 기록과 날짜별 경과, 예산 이력과 바이트 숫자, 마이그레이션 수, CI 실행 번호, 충돌을 푼 이야기.
이것들은 해당 블록 안이나 `docs/history.md`, `docs/work-status.md`에 둡니다.

## 9. README 숫자를 고치는 도구

- `check:doc-numbers`(`scripts/check-doc-numbers.mjs`)는 README의 문장 꼴을 찾아 숫자를 대조합니다. 문장을 바꾸면
  그 행의 패턴도 함께 고칩니다.
- 첫 화면 바이트를 고치는 로컬 도구(`readme_fp.sh`)는 「개발 노트」 블록의 「첫 화면을 N바이트(예산 N)로」와
  「생성물」 블록의 「YYYY-MM-DD 기준 N바이트」, 줄 머리의 「N·N바이트로」를 찾습니다. 그 문장 꼴은 그대로 둡니다.
- `tests/unit/deploy-policy.test.mjs`는 「배포와 운영」 블록의 헤더 표(`| 경로 | 헤더 | 값 |`)를 읽습니다. 이 표는
  3열이고 표 그대로 둡니다.
