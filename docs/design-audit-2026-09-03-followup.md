## 먼저 알아야 할 것

1차 감사가 고친 두 가지는 실측으로 확인됩니다. 유휴 6초 동안 플레이 화면의 DOM 변경은
**30건이고 전부 타이머 텍스트와 진행 막대**입니다 — 초당 한 번 화면 전체를 다시 그리던
문제는 사라졌습니다. 케이스별 고정 전략 시뮬레이션에서 세 열은 각각 다른 자원에서 최고이고
다른 자원에서 최저입니다.

새로 드러난 것의 성격은 1차와 다릅니다. 1차는 "기계가 주장과 다르다"였고, 2차는 **"측정
장치가 측정을 하지 않는다"**입니다. 점수 100점 중 20점을 차지하는 축이 어떤 플레이에서도
같은 값을 냅니다. 그 다음이 데이터의 이름 충돌이고, 그 다음이 확정 버튼이 화면 밖에서
나타나는 문제입니다.

## 점수 (S · 3건)

### S-1 【높음】 관점 전환 점수가 어떤 플레이에서도 100입니다

`cognitionScore`는 버스트 점수의 20%입니다. 그런데 상한 계산이 너무 쉽게 채워져서, 다섯 가지
서로 다른 전략을 전부 시뮬레이션해도 값이 움직이지 않습니다. 상수는 순위를 만들지 못하므로,
실질적으로 버스트 점수는 100점이 아니라 80점 만점입니다.

```
cognitionScore = clamp(고유 인지유형 × 14 + 유형 전환 × 10 + min(판단수,5) × 4, 0, 100)
  인지유형 4종만 등장해도 56, 전환 5회면 이미 106  → 12판단 케이스에서 항상 상한

실측 (케이스 6개 평균, 응답 15초 고정)
  항상 1번   버스트 50  기준유지 49  관점전환 100
  항상 2번   버스트 47  기준유지 42  관점전환 100
  항상 3번   버스트 45  기준유지 21  관점전환 100
  번갈아     버스트 43  기준유지 27  관점전환 100
  1/3 교대   버스트 49  기준유지 27  관점전환 100
```

**고칠 곳** — 가중치를 계수로 만들지 말고 분포를 만드십시오. 전환 횟수 대신 *한 유형에
얼마나 쏠렸는가*(엔트로피)를 쓰면 같은 데이터로 0~100이 실제로 벌어집니다. 또는 이 축을
없애고 20%를 기준 유지와 반영에 나눠 주십시오.

### S-2 【중】 새 기준 유지 축의 실측 폭이 21~49입니다

1차에서 리듬 대신 세운 축입니다. 방향이 맞는 축이지만, 고정 전략들 사이의 실측 격차가
28점뿐이라 28% 가중치가 총점을 8점밖에 움직이지 못합니다. 버스트 총점이 43~50에 몰려
랭킹의 해상도가 낮습니다.

**고칠 곳** — 압박 아래 판단에 주는 가중치를 2배에서 3~4배로 올리고, 방향을 바꾼 판단에
직전 방향 대비 페널티를 넣으십시오. 한 번도 흔들리지 않은 런과 매번 바뀐 런이 같은 축에서
20점 차이라면 축이 아닙니다.

### S-3 【중】 자유입력을 한 번도 쓰지 않으면 20점이 시작부터 빠집니다

`reflectionScore`는 20% 가중치인데 자유입력 신호와 자유입력 횟수로만 올라갑니다. 선택지만
쓰는 플레이는 이 축이 0에서 시작합니다. 1차에서 자유입력 판정을 엄격하게 만들었으므로
(최소 24자·한 문장) 이 격차는 더 벌어졌습니다.

**고칠 곳** — 의도라면 UI에서 그렇게 말해야 합니다("선택지 밖 계획이 점수의 20%입니다").
의도가 아니라면 선택지 안에서도 근거를 남기는 행동(에코 확인, 증거 복구, 메모 열람)에
반영 점수를 배분하십시오.

## 데이터 구조 (D · 3건)

### D-1 【높음】 선택지 id 25개가 서로 다른 장면에서 재사용됩니다

`choiceVoiceLines`와 `echoReplies`는 선택지 id로 조회합니다. 그런데 id가 장면마다 고유하지
않아서, 서로 다른 판단이 같은 대사를 말합니다. 304개 고정 선택지의 대사 중 고유한 것은
215줄이고, **89줄(29%)이 다른 장면과 공유**됩니다.

```
id "investigate"
  start      | 추가 자료를 먼저 요청한다        | {"time":-10,"trust":2,"fatigue":2}
  accounting | CFO와 회계팀을 분리 면담한다     | {"time":-8,"legitimacy":2,"fatigue":2}
  대사(공유) | "결론을 미루는 사람처럼 보일 위험을 감수하고, 원자료를 더 보자고 한다."

id "sale"     start / competitor 공유
id "disclosure"  accounting / payday 공유
id "negotiate"   payday / competitor 공유
id "free"     44개 장면이 공유
```

두 번째 장면에서 그 대사는 사실과 다릅니다. 자료를 더 보자고 한 적이 없습니다.

**고칠 곳** — 선택지 id에 장면 접두사를 붙이십시오(`accounting_investigate`). 생성 장면은
이미 `${id}_choice_${n}` 규칙을 쓰고 있으니, 집필 장면만 맞추면 됩니다. 세이브 호환은
로그가 `nodeId`를 이미 함께 기록하므로 읽기 쪽에서 흡수할 수 있습니다.

### D-2 【중】 케이스 오프닝 15개가 기준 장면의 선택지를 그대로 복제합니다

`caseOpeningRoutes`는 직전 케이스 결과에 따라 다른 오프닝으로 보냅니다. 그런데
`branchOpeningCopy`가 바꾸는 것은 제목·화자·서술·메모뿐이고, 선택지는
`nodes[baseNodeId].choices.map((choice) => ({ ...choice }))`로 **id·라벨·효과까지 동일**하게
복제됩니다. 세 갈래 오프닝이 도입부 문단만 다른 같은 판단입니다.

**고칠 곳** — 오프닝마다 최소 한 개의 선택지는 그 갈래에서만 가능한 것으로 바꾸십시오.
1차에서 연결 장면에 넣은 네 번째 축과 같은 방식이고, 15개 중 한 개씩이면 충분합니다.

### D-3 【중】 humanCost 분포가 케이스마다 25%에서 65%까지 벌어집니다

1차에서 전체 평균을 46%로 올렸지만, 케이스별로 보면 고르지 않습니다. 주제가 정점에 오는
마지막 사건이 가장 낮습니다.

```
case01 33/53 (62%)   case02 22/52 (42%)   case03 13/52 (25%)
case04 26/52 (50%)   case05 34/52 (65%)   final  11/43 (26%)
피로 회복 선택지      case05 5개,  final 6개  (케이스당 52개 중)
```

**고칠 곳** — `scripts/check-balance.mjs`의 humanCost 검사를 전체 평균이 아니라 케이스별
하한(예: 35%)으로 바꾸고, case03과 final의 효과표를 그 기준까지 채우십시오.

## UI · UX (U · 2건)

### U-1 【높음】 확정 버튼이 화면 밖에서 나타나 0.7초 동안 올라옵니다

휴대폰(390×844)에서 선택지를 고르면 확정 콘솔이 열립니다. 그 순간 확정 버튼의 위치는
`top = 1,639px`, 즉 **뷰포트 아래 두 화면 밖**입니다. 부드러운 스크롤이 이를 730px까지
끌어올리는 데 700ms가 걸리고, 그 뒤로도 프레임이 계속 움직입니다.

```
프레임별 확정 버튼 top (390×844)
   58ms 1639   100ms 1637   134ms 1617   166ms 1556
  199ms 1413   233ms 1127   ...   700ms 730
40프레임 중 15프레임에서 위치가 바뀜
```

그 사이의 탭은 버튼이 있던 자리가 아니라 지나가는 다른 요소에 떨어집니다. 실제 확정 처리
자체는 44ms로 빠릅니다 — 느린 것은 계산이 아니라 버튼을 따라가는 일입니다.

**고칠 곳** — 확정 콘솔을 문서 흐름이 아니라 뷰포트 하단 고정(`position: fixed`)으로 띄우고
스크롤 애니메이션을 없애십시오. 이미 `.commit-console`에 모바일 sticky 규칙이 있으니, 여는
순간의 스크롤을 제거하는 것만으로 대부분 해결됩니다.

### U-2 【중】 상태판이 자원 레일과 같은 것을 두 번 보여줍니다

1차에서 넣은 자원 레일이 상단에 고정되면서, 화면 맨 아래 상태판(820px)의 자원 목록은 같은
숫자를 반복합니다. 모바일 플레이 화면은 4,313px이고 선택 패널은 1,596px 지점입니다.

```
모바일 구성 (390px)
  헤더 315  레일 110  장면 946  선택 패널 1,839  상태판 820
```

**고칠 곳** — 상태판의 자원 목록을 모바일에서 접고, 레일에 없는 것(누적 기록, 인물, 진행률)만
남기십시오. 상태판 820px 중 절반이 줄면 화면은 4화면 아래로 내려갑니다.

## 운영 (O · 1건)

### O-1 【중】 아트 변형을 다시 만드는 절차가 문서에만 있습니다

`npm run check:art`는 변형의 존재와 용량을 검사하지만, 만들지는 못합니다. 원본을 교체하면
브라우저 캔버스로 다시 뽑는 절차를 사람이 기억해서 실행해야 합니다.

**고칠 곳** — 그 절차를 `scripts/build-art-variants.mjs`로 넣으십시오. Playwright는 이미
devDependency이므로 새 의존성이 필요 없고, `check:art`가 실패할 때 실행할 명령이 생깁니다.
