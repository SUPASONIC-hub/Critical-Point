# 새 사건 쓰는 법

이 문서는 사건 하나를 새로 쓰려는 사람을 위한 안내입니다. 코드를 깊이 몰라도 됩니다. 사건은 자바스크립트
파일 하나에 든 큰 객체 하나이고, 그 안의 글과 숫자만 채우면 나머지(장면 잇기, 카드 섞기, 장면 좌표 붙이기)는
게임이 불러올 때 알아서 합니다. 대신 검사 스크립트가 많은 규칙을 지키게 하므로, 아래 규칙을 먼저 읽으면
검사에서 덜 걸립니다.

사건을 JSON으로 빼지 않은 이유: 사건은 이미 사건마다 파일 하나로 나뉘어 있고, 검사가 그 내용을 읽어 그래프·
연도·대사·쉬운 말·카드 길이를 확인합니다. 형식을 바꾸는 것보다 이 문서와 실제 장면 견본이 기여를 더 쉽게
합니다.

가장 빠른 시작은 **가장 최근 사건 파일(사건 49)을 복사해서 고치는 것**입니다. 그 파일은 지금 검사가 요구하는
모양을 모두 갖추고 있습니다. 사건 01~11과 마지막 사건은 옛 표에서 옮겨 와 모양이 느슨하니 견본으로 쓰지
마십시오.

새 사건을 견본으로 게임에 넣어 두지는 않았습니다. 들어간 사건은 모두 시즌의 이야기이고, 이야기 없는 견본
사건은 검사(결말 퍼널, 시즌 완주)를 함께 바꾸게 하기 때문입니다. 대신 견본은 둘입니다. 1장의 **뼈대 견본**은
사건 49의 모양을 그대로 줄인 것이고, 4장은 실제 장면을 한 글자도 고치지 않고 옮긴 것입니다. 실제 파일 하나를
처음부터 끝까지 읽고 싶다면 지금 가장 짧은 사건 파일은 `src/nodes/case24.js`(약 850줄)입니다. 사건 12~49는
모두 850~870줄이라 어느 것을 읽어도 길이는 비슷합니다.

차례

1. 사건 하나에 들어가는 것 (뼈대 견본)
2. 장면 하나
3. 카드 하나
4. 견본: 실제 장면 하나
5. 나머지 표
6. 시즌에 사건을 올리기
7. 검사가 지키는 규칙
8. 쓰고 나서 돌릴 순서
9. 흔한 실수
10. 글 방향: 한국 직장의 블랙 코미디
11. 참고: 파일 위치

## 1. 사건 하나에 들어가는 것

사건 하나는 장면 20개입니다(첫 사건인 프롤로그 01만 오프닝이 없어서 17개). 그중 직접 쓰는 장면과 표는
이렇습니다.

| 칸(필드) | 무엇 | 몇 개 |
| --- | --- | --- |
| `id` | 사건 id. `case50`처럼 씁니다 | 1 |
| `nodes` | 본 장면. 브리핑(첫 장면)부터 결정 장면까지 | 정확히 5 |
| `aftermath` | 여파 장면. 사건을 닫는 장면이고, 이 장면의 카드 셋이 사건의 결말 셋이 됩니다 | 1 |
| `aftermathRoute` | `[결정 장면 id, 여파 장면 id]`. 결정 장면의 카드가 모두 여파로 갑니다 | - |
| `connectiveScenes` | 연결 장면. 본 장면 하나 뒤에 끼어드는 "기록 밖" 장면 | 정확히 3 |
| `reactionScenes` | 반응 장면. 연결 장면 하나마다 하나씩 뒤따름 | 정확히 3 |
| `branchPlan`, `branchScenes` | 샛길. 어떤 카드 하나를 고르면 두 장면짜리 샛길로 빠졌다가 본 길로 돌아옵니다 | 장면 2 |
| `routePlan` | 숨은 경로. "판을 다시 짠다" 카드가 처음 여는 경로와 그 마지막 장면 | 장면 2 |
| `evidencePlan` | 단서 반전. 정해진 장면들에 "단서를 연다" 카드를 붙이고, 그 카드가 가는 장면 | 장면 1 |
| `memoryPlan` | 기억 카드. 앞 사건에서 숨은 경로나 단서 반전을 지난 사람에게만 나오는 카드의 문구와 행선지 | - |
| `openingRoutes`, `openingCopy`, `openingSignatures` | 오프닝 셋. 앞 사건이 어떤 결말로 닫혔는지에 따라 브리핑이 셋으로 갈립니다 | 장면 3 |
| `characterProfiles` | 이 사건에서 처음 나오는 사람의 프로필. 새 인물이 없으면 `{}` | - |
| `setting`, `sceneContext` | 장소·시각·질문·첫 줄. 장면 20개 모두에 하나씩 | - |
| `clue` | 이 사건의 단서 카드 | 1 |
| `outcomes`, `carryovers`, `continuityChallenges` | 결말 셋의 문구, 다음 사건으로 넘기는 자원, 앞 사건 결말마다 이번 사건이 내는 과제 | - |

빠뜨리면 `check:graph`가 "is missing ..."으로, 아무도 읽지 않는 칸을 더하면 "has fields no module reads"로
실패합니다. 반드시 있어야 하는 칸이 아닌 것은 `characterOverrides`(이미 있는 인물이 이 사건에서만 달라지는 점),
`characterProfiles`, `openingLines`(오프닝 하나에서만 다르게 말하는 카드의 대사) 같은 몇 개뿐입니다.

### 이름 짓기

- 사건 id가 `case50`이면 장면 id는 모두 `c50_`으로 시작합니다. 아니면 검사가 실패합니다.
- 여파 장면은 `c50_aftershock`, 사건의 결과 화면은 `case50_result`입니다. 여파 장면 카드의 `next`는
  `case50_result`로 씁니다.
- 카드 id는 한 사건 안에서 겹치면 안 됩니다. 겹치면 뒤에 쓴 대사가 앞의 것을 덮어씁니다.
- 단서 id는 `c50-`으로 시작합니다(예: 사건 49의 `c49-successor-form`).
- 여파 카드 셋은 대부분의 사건이 `c50_after_warm`(사람 쪽), `c50_after_record`(기록 쪽), `c50_after_rush`(속도
  쪽)처럼 이름을 붙였습니다. 검사가 요구하는 것은 아니지만, 다음 사건과 마지막 사건이 이 id로 키를 쓰므로
  같은 이름을 쓰면 옮길 때 덜 헷갈립니다.

### 뼈대 견본

사건 49(`src/nodes/case49.js`)를 사건 50이라고 치고 칸만 남긴 모양입니다. `...`과 주석 자리를 채우면 검사가
읽는 모양이 됩니다. 각 칸의 자세한 모양은 2~5장에 있습니다.

```js
/**
 * CASE 50 -- 이 사건이 무엇을 다루는지 한두 문단. 지금까지는 영어로 써 왔습니다.
 */
const case50Nodes = {
  c50_start: {
    phase: "CASE 50 BRIEFING",
    title: "...",
    speaker: "한서윤",
    text: "...",
    memo: ["...", "..."],
    triggers: ["responsibility", "curiosity"],
    choices: [
      {
        id: "c50_start_share",
        label: "...", // 30자 이하
        effect: { trust: 10, time: -5, fatigue: 4 },
        voice: "이유를 말하며, + 라벨을 거의 그대로.",
        echo: "카드를 받아 이미 일어난 일로 여는 문장(~자, ~니). ...",
        next: "c50_market",
        cognition: { persistence: 2 },
      },
      // 사람 쪽·절차 쪽·속도 쪽이 하나씩 되도록 카드 둘 더
      { id: "reframe", label: "같은 일이 전에 어떻게 끝났는지 묻는다", type: "reframe", next: "c50_market" },
    ],
  },
  // c50_market ... 결정 장면 c50_final까지, 본 장면은 모두 다섯
};

export const case50 = {
  id: "case50",
  nodes: case50Nodes,
  aftermath: {
    c50_aftershock: { phase: "AFTERMATH", title: "...", speaker: "...", text: "...", memo: [], triggers: [], choices: [/* 결말 카드 셋, next: "case50_result" */] },
  },
  aftermathRoute: ["c50_final", "c50_aftershock"],
  connectiveScenes: [/* 셋: { id, after, next, title, speaker, text, memo, choices } -- 카드에 id·next 없음 */],
  reactionScenes: [/* 셋: after가 연결 장면 id */],
  branchPlan: ["c50_market", 0, "c50_branch_x", "c50_branch_x_follow"],
  branchScenes: { c50_branch_x: { /* ... */ }, c50_branch_x_follow: { /* ... */ } },
  routePlan: { /* 5장 */ },
  evidencePlan: { /* 5장 */ },
  memoryPlan: { systemNext: "...", evidenceNext: "...", systemLabel: "...", evidenceLabel: "...", systemEcho: "...", evidenceEcho: "..." },
  openingRoutes: { c49_after_warm: "c50_start_warm", c49_after_record: "c50_start_record", c49_after_rush: "c50_start_rush" },
  openingCopy: { c50_start_warm: ["제목", "화자", "본문", ["메모"]] /* 셋 모두 */ },
  openingSignatures: { c50_start_warm: { label: "...", effect: {}, cognition: {}, voice: "...", echo: "..." } /* 셋 모두 */ },
  characterProfiles: {},
  setting: { place: "...", clock: "10월 초 목요일 · 09시" },
  sceneContext: { c50_start: { place: "...", clock: "...", question: "...", lead: "..." } /* 장면 20개 모두 */ },
  clue: { id: "c50-...", title: "...", text: "..." },
  outcomes: { c50_after_warm: { tag: "...", title: "...", text: "..." } /* 셋 모두 */ },
  carryovers: { c50_after_warm: { trust: 10, fatigue: -5 } /* 셋 모두 */ },
  continuityChallenges: { c49_after_warm: { id: "protect-trust", title: "...", text: "..." } /* 셋 모두 */ },
};
```

키 두 종류를 헷갈리지 않게 봅니다. `openingRoutes`와 `continuityChallenges`는 **앞 사건**(사건 49)의 여파 카드
id로 키를 쓰고, `outcomes`와 `carryovers`는 **이번 사건**의 여파 카드 id로 씁니다.

## 2. 장면 하나

본 장면(`nodes`) 하나는 다음 칸을 씁니다.

| 칸 | 뜻 |
| --- | --- |
| `phase` | 장면 위 작은 칩에 찍히는 영어 대문자 글. 예: `"CASE 49 BRIEFING"`, `"FINAL DECISION"`. 키로 읽히지 않는 순수한 화면 문구입니다 |
| `title` | 장면 제목 |
| `speaker` | 이 장면에서 말하는 사람. 시즌에 프로필이 있는 사람이어야 합니다 |
| `text` | 본문(내레이션). 쉬운 말 검사가 읽는 곳입니다. **420자 이하**로 쓰고, 첫 문장은 날짜·시각이 아니라 행동이나 이미지로 엽니다(아래) |
| `memo` | 메모 줄 목록. 짧은 문자열 배열 |
| `triggers` | 이 장면이 건드리는 감정 키 목록(아래 표) |
| `choices` | 카드 목록 |

**본문의 첫 문장** — 날짜와 시각은 장면 좌표의 `clock`이 본문 바로 위에 찍습니다. 본문을 "2025년 10월 17일
금요일 아침 아홉 시, ..."로 열면 같은 말을 두 번 읽힙니다(10월 22일에 장면 본문 1,129개 가운데 333개가 숫자나 요일·때로
시작했습니다). 첫 문장은 누가 무엇을 하는지, 무엇이 보이는지로 엽니다. 예: "도윤하가 공지문을 출력해 들고
옵니다." 날짜가 이야기에 꼭 필요하면 둘째 문장 뒤에 둡니다.

장면이 무슨 종류인지(`kind`), 어느 사건인지(`caseId`), 압박 장면인지(`pressure`)는 게임이 붙이므로 쓰지
않습니다. 압박 장면으로 보이게 하려면 장면 좌표에 `pressure: true`를 쓰거나 압박 장면 목록에 id를 더합니다.

**감정 키(`triggers`)** — 이 안의 것만 씁니다.

| 키 | 화면 | 키 | 화면 |
| --- | --- | --- | --- |
| `protection` | 보호 | `trust` | 신뢰 |
| `injustice` | 부당함 | `affection` | 애정 |
| `revenge` | 복수 | `recognition` | 인정 |
| `responsibility` | 책임 | `fear` | 공포 |
| `competition` | 경쟁 | `system` | 시스템 |
| `reward` | 보상 | `helplessness` | 무력감 |
| `curiosity` | 호기심 | `selfAwareness` | 자기 인식 |
| `order` | 질서 | `manipulation` | 조종 |
| | | `choice` | 선택 |

## 3. 카드 하나

카드 하나는 `{ id, label, effect, voice, echo, next, cognition }` 객체 하나입니다.

| 칸 | 뜻 |
| --- | --- |
| `id` | 카드 id |
| `label` | 카드에 찍히는 문구. **30자 이하**로 씁니다(7장 참고) |
| `effect` | 이 카드가 자원을 얼마나 움직이는지. 아래 여섯 키만 씁니다 |
| `voice` | 카드를 고른 뒤 분석관이 하는 말. "이유, + 라벨을 거의 그대로" 모양입니다 |
| `echo` | 고른 뒤 돌아오는 반응. 카드를 받아 **이미 일어난 일로** 여는 문장으로 시작합니다("찾아가자 ...", "조항을 읽으니 ..."). "찾아가면 ..." 같은 가정형은 쓰지 않습니다(아래) |
| `next` | 다음 장면 id. 게임이 정하는 경우에는 **쓰지 않습니다**(아래) |
| `cognition` | 이 카드가 어떤 생각 방식을 쓰는지(아래) |

**echo는 일어난 일로 엽니다** — 카드는 이미 골랐고, `echo`는 그 뒤에 일어난 일입니다. "솔직하게 말하면 한지우가
받아 적습니다"처럼 `~면`으로 열면 아직 하지 않은 일을 가정하는 말로 읽힙니다(10월 22일에 `echo` 3,778개
가운데 2,156개가 이렇게 열렸습니다). `~자`, `~니`로 엽니다.

| 쓰지 않음 | 씀 |
| --- | --- |
| 찾아가면 떡집 셔터에 쪽지가 붙어 있습니다. | 찾아가자 떡집 셔터에 쪽지가 붙어 있습니다. |
| 조항을 읽으면 '그 임직원'이라는 단어가 눈에 걸립니다. | 조항을 읽으니 '그 임직원'이라는 단어가 눈에 걸립니다. |
| 아들을 찾으면 서류는 생깁니다. | 아들을 찾자 서류가 생깁니다. |

**자원(`effect`)** — 키는 이 여섯 개뿐이고, 숫자는 더하고 빼는 양입니다.

| 키 | 화면 이름 | 올라가면 |
| --- | --- | --- |
| `time` | 남은 시간 | 좋음 |
| `capital` | 현금 | 좋음 |
| `trust` | 믿음 | 좋음 |
| `legitimacy` | 공정함 | 좋음 |
| `humanCost` | 사람 피해 | **나쁨** |
| `fatigue` | 피로 | **나쁨** |

사람 피해와 피로는 숫자가 올라가는 것이 손해입니다. `fatigue: -3`은 쉬었다는 뜻입니다.

**생각 방식(`cognition`)** — 키는 네 개입니다.

| 키 | 화면 이름 |
| --- | --- |
| `persistence` | 끝까지 버티기 |
| `inference` | 꼼꼼히 확인하기 |
| `reframing` | 판 바꾸기 |
| `risk` | 위험 다루기 |

- 직접 쓰는 카드(본 장면, 여파, 샛길, 숨은 경로, 단서 반전)는 `cognition`을 **반드시** 씁니다. 한두 가지,
  무게는 각각 1~3입니다. 예: `{ inference: 2, persistence: 1 }`.
- 연결·반응 장면의 카드는 쓰지 않아도 됩니다. 쓰지 않으면 게임이 라벨의 낱말("확인", "끝까지", "바로" 같은
  것)과 가장 크게 오르는 자원으로 읽어 냅니다. 이 읽기는 "빼지 않고"를 "빼"로 읽는 식으로 틀릴 수 있으니,
  틀리게 읽히는 카드에만 직접 씁니다. 이때는 **한 가지만**, 판 바꾸기는 2, 나머지는 1로 씁니다.
- 라벨을 고쳐서 읽기를 유도하지 마십시오. 라벨은 플레이어가 읽는 글입니다. 생각 방식은 결말 판정에 들어갑니다.

**판을 다시 짠다 카드** — 본 장면은 마지막에 이 카드를 둡니다. 생각 방식과 효과는 게임이 정하므로 쓰지
않습니다(`REFRAME_COGNITION`; 라벨을 읽지 않으니 `cognition`도 쓰지 않습니다). 라벨은 그 사건의 숨은 경로가
실제로 하는 일을 20자 안팎 한 줄로 씁니다. 한때 204장이 모두 "다른 방법을 제안한다"여서 무엇이 열리는지
알 수 없었습니다. 예: "이런 오차가 전에 어떻게 끝났는지 묻는다", "연장된 대출들이 어떻게 끝났는지 늘어놓는다".

```js
{
  id: "reframe",
  label: "같은 일이 전에 어떻게 끝났는지 묻는다", // 숨은 경로가 하는 일
  type: "reframe",
}
```

**`next`를 언제 쓰나** — 게임은 불러올 때 장면을 다시 잇습니다. 연결 장면은 자기가 따라가는(`after`) 장면의
카드를 모두 가져가고, 결정 장면의 카드는 여파로 갑니다. 그래서 그런 카드에는 `next`를 쓰지 않습니다. `next`를
썼다면 조립된 그래프가 실제로 쓰는 값과 같아야 하고, 다르면 `check:graph`가 "drop the dead next"로 실패합니다.
사건 49를 보면 브리핑 카드는 `next: "c49_market"`을 쓰고, 그 뒤 장면(`c49_market`)의 카드는 연결 장면이
가져가므로 `next`가 없습니다.

사건 12의 브리핑 장면 `c12_start`를 그대로 옮깁니다(파일에서 고친 것 없음).

읽을 점:

- **장면 id와 카드 id**가 모두 `c12_`로 시작하고, 카드 id는 `장면id_짧은말` 모양입니다.
- **본문의 어려운 말**: "부제소 합의" 바로 뒤에 괄호로 풀이가 붙어 있습니다. "국정감사"는 이 본문에서 풀이가
  없지만, 같은 장면의 장면 좌표 `lead`(본문보다 먼저 읽히는 첫 줄)에서 이미 풀었습니다(아래). 쉬운 말 검사는
  `lead`와 `text`를 이어서 읽습니다.
- **카드 셋의 모양**: 사람 쪽(믿음↑), 절차 쪽(공정함↑), 속도 쪽(현금·시간↑)이 하나씩이고, 각 카드는 얻는 만큼
  다른 자원을 잃습니다. 카드 순서는 게임이 장면마다 정해진 방식으로 섞으므로, 쓴 순서대로 나오지 않습니다.
- **voice**는 "이유, + 라벨"입니다. "서류보다 사람이 먼저라며, 피해자 모임 대표부터 직접 찾아간다."
- **echo**는 카드를 받아 엽니다. 이 견본은 파일 그대로라 `~면`으로 열지만("찾아가면 ...", "조항을 읽으면 ..."),
  새로 쓸 때는 3장 규칙대로 일어난 일로 엽니다("찾아가자 ...", "조항을 읽으니 ..."). 옛 사건의 `~면`은 11월
  2일 뒤에 고칩니다.
- **next**: 브리핑 카드는 다음 본 장면으로 직접 갑니다. 이 사건에서는 그 값이 조립된 그래프와 같아서 써 둔
  것입니다.
- **cognition**: 직접 쓴 카드라 하나씩 적혀 있습니다. 판을 다시 짠다 카드에는 없습니다.

같은 장면의 장면 좌표(`sceneContext`)는 이렇습니다.

```js
    c12_start: {
      place: "트리거랩 4층 분석관실",
      clock: "분쟁조정 신청 마감까지 D-10",
      question: "300억 배상안에 '다시는 소송하지 않는다'는 조건이 붙었습니다. 무엇부터 하겠습니까?",
      lead: "국정감사(국회가 공개적으로 따져 묻는 자리)가 끝나고 2주, 분석관실 프린터에서 그룹 공지문이 계속 나옵니다.",
    },
```

- `place`, `clock`은 화자 위에 찍힙니다. 비워 두면 같은 사건에서 바로 앞에 놓인 장면의 것을, 그것도 없으면 사건의 `setting`을 씁니다.
- `question`은 카드 위에 나오는 한 줄 질문입니다.
- `lead`는 본문을 여는 첫 줄입니다. 어떤 장면을 먼저 지났는지에 기대지 않게 씁니다. 경로에 따라 앞 장면을
  건너뛰고 들어올 수 있기 때문입니다.

연결 장면은 더 짧습니다. 같은 사건의 `c12_line`입니다.

## 5. 나머지 표 (사건 49를 보며 채우기)

- **여파(`aftermath`)**: 장면 하나. 카드 셋이 사건의 결말 셋이고 `next`는 결과 화면(`case50_result`)입니다.
  `outcomes`, `carryovers`는 이 카드 id 셋으로 키를 씁니다. `outcomes`는 `{ tag, title, text }`,
  `carryovers`는 다음 사건으로 넘길 `effect`와 같은 모양의 숫자입니다.
- **오프닝**: `openingRoutes`는 **앞 사건 여파 카드 id → 이번 사건 오프닝 장면 id**입니다. 키는 앞 사건의
  접두어(예: `c49_after_...`)여야 합니다. `openingCopy`는 오프닝 장면마다 `[제목, 화자, 본문, 메모 배열]`이고,
  `openingSignatures`는 그 오프닝에서만 나오는 넷째 카드입니다. 오프닝 장면의 나머지 카드는 브리핑 카드를
  복사해서 씁니다.
- **과제(`continuityChallenges`)**: `openingRoutes`와 같은 키로 `{ id, title, text }`를 씁니다. `id`는
  `protect-trust`, `repair-legitimacy`, `find-cost`, `use-reframe`, `lower-risk`, `avoid-risk` 중 하나이고,
  그 오프닝에 그 과제를 채울 카드가 실제로 있어야 합니다(예: `protect-trust`면 믿음이 오르는 카드).
- **샛길**: `branchPlan`은 `[장면 id, 카드 순번(0부터), 샛길 첫 장면 id, 샛길 둘째 장면 id]`입니다. 다섯째
  칸에 문 여는 조건 이름을 쓰면 그 조건에서만 열립니다. 샛길 둘째 장면의 카드는 본 길로 돌아갑니다(사건 49는
  연결 장면 `c49_parcels`로).
- **숨은 경로(`routePlan`)**: `start`, `result`(여파 장면 id), `defaultFree`(판을 다시 짠다가 처음 여는 장면),
  `choices: {}`, `system`(경로 장면과 마지막 장면의 글, `routeChoices` 셋, `finalTitle`·`finalText`·
  `finalMemo`), `finalChoices` 셋(`id`는 `"a"`, `"b"`, `"c"`). 마지막 장면의 글을 비우면 시즌 공용 장면으로
  닫히는데, 지금은 검사가 그것을 실패로 봅니다.
  경로 장면 본문의 첫 문장은 "A할지 고르는 대신 B하자 C가 N건을 엽니다" 한 문장으로 몰지 않습니다. 시즌의 숨은
  경로 54개가 모두 이 틀(평균 87자)이었습니다. 행동(무엇을 묻거나 하는지) → 누가 움직이는지 → 무엇이 열리는지를
  짧은 문장 셋으로 나누고, 사건마다 동사와 리듬을 바꿉니다.
- **단서 반전(`evidencePlan`)**: `sourceRoutes`에 적은 장면마다 "단서를 연다" 카드(`entryLabel`)가 붙고,
  그 카드는 `requiredAuthority` 권한이 있어야 열립니다. `entryVoice`, `entryEcho`, `entryEffect`, 장면 글,
  카드 셋을 씁니다.
- **기억 카드(`memoryPlan`)**: 앞 사건이 넘길 수 있는 기억마다 카드 문구(`systemLabel`/`evidenceLabel`),
  행선지(`systemNext`/`evidenceNext`), 반응(`systemEcho`/`evidenceEcho`)을 씁니다. 앞 사건이 넘길 수 없는
  기억의 카드를 쓰면 그것도 실패합니다.
- **인물(`characterProfiles`)**: 새 화자마다 `role`, `stance`, `job`, `appearance`, `thought`, `gesture`,
  `voice`, `line` 여덟 칸을 모두 씁니다. 시즌에 이미 있는 이름을 다시 넣으면 실패합니다. 그 사람이 이 사건에서만
  달라지는 점은 `characterOverrides`에 씁니다.

## 6. 시즌에 사건을 올리기

사건 파일을 쓴 뒤 시즌에 올리는 곳은 아래와 같습니다. 사건 50을 마지막 사건 앞에 넣는다고 하면:

1. **사건 목록**: 사건 목록 파일에서 새 파일을 불러와(import) 목록의 마지막 사건 바로 앞에 넣습니다. 이 목록은
   어느 사건이 자기 표를 가지는지만 말하고, 순서는 정하지 않습니다.
2. **시즌 순서와 문**: 사건 표 파일에서
   - 시즌 순서(`CASE_SEQUENCE`)의 `"final"` 앞에 `"case50"`을 넣습니다.
   - 시작 장면(`CASE_START_NODES`)에 `case50: "c50_start"`,
   - 결과 장면(`CASE_RESULT_NODES`)에 `case50: "case50_result"`,
   - 쓴 장면 순서(`authoredNodeOrders`)에 본 장면 다섯 개를 쓴 순서대로,
   - 사건 목표(`caseObjectives`)에 한 줄,
   - 사건 카드(`seasonCasesBase`)에 `id`, `label`("사건 50"), `title`, `trigger`, `status`, `summary`.
3. **이어지는 곳 옮기기**: 마지막 사건의 오프닝(`openingRoutes`)과 과제(`continuityChallenges`)는 바로 앞
   사건의 여파 카드 id로 키를 씁니다. 지금은 `c49_after_*`이므로 `c50_after_*`로 바꿉니다. 사건이 앞에 끼어들
   때마다 이렇게 옮겨 왔습니다.
4. **사건 둘레의 문구**: 이동 경로와 이유(`operatorBriefs`), 챕터 규칙(`chapterRules`), 사건이 끝난 뒤
   예고(`nextCaseSignals` — 사건 49의 예고가 이제 사건 50을 가리키게 고치고, 사건 50의 예고는 마지막 사건을
   가리키게 새로 씁니다), 막간(`seasonInterludes`), 사건을 열 때 에코의 말(`caseIntroEchoes`), 관찰 항목
   (`triggerLabSignals`), 음악 모티프(`chapterMotifs`). 이 중 몇은 빠뜨려도 검사가 통과하고 다른 사건의 문구나
   기본값이 대신 나오므로, 사건 49의 항목을 보고 빠짐없이 씁니다.
5. **압박 장면**(선택): 방이 조여 드는 장면이면 압박 장면 목록에 id를 넣거나 장면 좌표에 `pressure: true`를
   씁니다. 결정·여파·경로 마지막 장면은 원래 압박 장면입니다.
6. **서버의 사건 목록**: 랭킹 서버는 시즌 사건 목록(`season_case_ids()`)을 따로 들고 있고, 클라이언트의
   `CASE_SEQUENCE`와 같아야 시즌 완주 기록을 받습니다. 그 함수를 새 목록으로 다시 정의하는 마이그레이션을
   더합니다(`check:grants`가 비교합니다). 마이그레이션은 main에 병합되면 1분 안에 적용됩니다.
7. **숫자를 적은 문서와 검사**: README에는 사건 수와 용어집 수 같은 숫자가 적혀 있고 `check:doc-numbers`가
   그 숫자를 코드에서 다시 셉니다. 대사 검사(`check:dialogue`)는 연결·반응 장면의 총수를 기대값으로 들고
   있어서, 사건 하나를 더하면 그 값도 6만큼 올려야 합니다.

브라우저 빌드는 따로 등록할 것이 없습니다. 앱 빌드는 빌드할 때 같은 사건 파일로 시즌 그래프를 Node에서 한 번
만들고, 그 결과를 `virtual:season`(공통 색인)과 `virtual:season-case/<사건 id>`(사건 하나씩) 모듈로
나눠 줍니다. 개발 서버에서 사건 파일을 고치면 데이터를 다시 만들고 페이지를 새로 엽니다.

### 6-1. 번외 사건은 시즌에 올리지 않습니다 (E-11)

번외 사건은 시즌 밖의 짧은 사건(장면 8~12개, 판 한 번, 결말 셋)입니다. 위 1~7을 하나도 하지 않습니다.
`CASE_SEQUENCE`·사건 목록·서버의 사건 목록이 그대로라 점수 상한, 목표, 칭호, 랭킹이 바뀌지 않습니다.

1. **파일**: `src/nodes/sideNN.js`(예: `side01.js`)에 `export const side01 = { ... }`. 모양은 견본
   `src/nodes/side00.js`(틀 확인용, 출시 빌드에 없음)를 따릅니다. id는 `sideNN`이고 `caseNN`은 쓰지 않습니다
   (서버는 `^case[0-9]{2}$`만 시즌 사건으로 받습니다). 장면은 `s1_`로 시작하고, 마지막 장면 `s1_aftershock`의
   카드 셋이 `s1_result`로 가며, 그 카드 id마다 `outcomes`에 결말 하나(`title`, `text`)를 씁니다. 시작 자원은
   `startState.resources`에 직접 씁니다(시즌 자원을 읽지 않습니다).
2. **목록**: `src/nodes/sidePacks.js`의 `SIDE_CASES`에 `{ id, label: "번외 1", title, load }` 한 줄. 목록이 비어
   있으면 시작 화면의 칸이 보이지 않습니다.
3. **검사**: `check:graph`가 `src/nodes/side*.js`를 모두 걸어 봅니다(`checkSidePack`, `src/state/sidePackCheck.js`).
   `check:canon`·`check:plain-language`·`check:card-labels`·`check:text`는 `src/nodes`의 모든 파일을 이미 읽습니다.
4. **기록**: 이 기기의 `critical-point-side-cases-v1`에 끝낸 표시와 진행 중인 판만 남습니다. 서버 행, 랭킹,
   시즌 저장, NEW GAME+, 클라우드 저장에는 아무것도 가지 않습니다(`tests/unit/side-cases.test.mjs`).

## 7. 검사가 지키는 규칙

모두 `npm run verify:static`에 들어 있습니다. 하나씩 돌릴 때는 `npm run check:graph`처럼 씁니다.

### check:graph — 그래프와 사건 모양

- 사건 모양: 1장의 칸이 모두 있고, 장면 20개(본 장면 5, 연결 3, 반응 3, 샛길 2, 오프닝 3 ...)이고, 반응
  장면이 연결 장면을 하나씩 따라가고, 장면 20개 모두에 장면 좌표가 있어야 합니다.
- 장면마다 제목·본문·카드가 있고, 카드마다 id·라벨·`next`(조립 뒤)가 있어야 합니다. `effect`와
  `cognition`의 키는 위 표의 것만, 숫자는 유한한 수여야 합니다.
- 다른 사건의 장면이나 결과 화면으로 가는 카드는 안 됩니다.
- 쓴 장면은 모두 어떤 길로든 닿아야 하고, 모든 장면에서 결과 화면까지 갈 길이 남아 있어야 합니다. 앞 장면으로
  되돌아가는 카드는 안 됩니다(효과가 두 번 붙습니다).
- 직접 쓴 카드는 모두 `voice`와 `echo`가 있어야 합니다. 비어 있으면 게임이 대신 만든 문구가 나가는데, 지금은
  그것이 하나만 있어도 실패입니다.
- 결말마다 `outcomes`, `carryovers`, 다음 사건의 과제가 있어야 하고, 과제는 그 오프닝의 카드로 채울 수 있어야
  합니다.
- 화자마다 여덟 칸짜리 인물 프로필이 있어야 합니다.

### check:canon — 사실과 연도

- 모든 사건이 같은 대출 하나(대출번호 2023-0412, 310억)에 매달려 있으므로, 그 대출의 사실(번호, 금액, 심사
  날짜, 반려 시각, 부채비율 같은 것)을 적을 때는 정해진 값만 씁니다. 사실 목록과 그 이유는 시즌 사실 문서에
  있습니다. 다른 값이 꼭 필요하면 이야기와 함께 그 문서와 검사 표를 같이 고칩니다.
- **요일이 붙은 날짜는 그 해의 달력과 맞아야 합니다.** 연도를 적지 않은 날짜는 파일로 연도를 정합니다.

  | 파일 | 연도 |
  | --- | --- |
  | 프롤로그 01 | 2022 |
  | 프롤로그 02~05 | 2023 |
  | 사건 01~18 | 2025 |
  | 사건 19~마지막 사건 | 2026 |
  | 사건 목록·사건 문구처럼 모든 사건을 요약하는 파일 | 넷 중 아무 해 |

  예: 사건 50에 "10월 16일 금요일"이라고 쓰면 2026년 10월 16일이 금요일인지 확인합니다. 날짜에 "2025년"을
  직접 붙이면 그 해로 확인합니다.

### check:dialogue — 대사가 카드를 받는가

연결·반응 장면에서 각 카드의 `voice`가 자기 라벨과 낱말을 충분히 나누는지, 그리고 다른 카드의 `voice`가 그
라벨에 더 잘 맞지는 않는지 봅니다. `echo`는 첫 문장의 순서를 봅니다. 대사를 다른 카드 자리에 잘못 붙였을 때
잡히는 검사입니다. `voice`에 라벨을 거의 그대로 넣고, `echo`를 그 카드를 받는 말로 열면 걸리지 않습니다.

### check:plain-language — 쉬운 말

- **쓰지 않는 말**: 여신·융자(→ 대출), 품의(→ 승인 요청), 기안(→ 작성), 결재(→ 승인), 금번(→ 이번),
  익일(→ 다음 날), 불입(→ 납입), 수순(→ 순서). "전자결재", "재기안"처럼 붙여 써도 잡힙니다.
- **판을 다시 짠다는 글로 쓰는 칸이 아닙니다**: "자유 응답", "입력한 문장"처럼 플레이어가 문장을 쓴 것처럼
  말하는 표현은 안 됩니다.
- **용어집의 말은 사건에서 처음 읽히는 곳에서 괄호로 풉니다.** 바로 뒤에, 또는 세 글자 이내의 낱말 하나 뒤에
  괄호를 엽니다. 예: "부제소 합의(앞으로 이 일로 소송하지 않겠다는 약속)", "엠바고(약속한 시각까지 보도를
  미뤄 두는 것)". "처음"은 시즌이 아니라 사건마다이고, 길마다 따집니다. 오프닝 셋 어느 것으로 들어와도, 어느
  카드를 골라 와도 그 장면에 오기 전에 풀이를 지났어야 합니다. 그래서 오프닝 장면이 그 말을 쓰면 각자 풉니다.
  읽는 곳은 본문(`text`)과 첫 줄(`lead`)뿐이고, 라벨과 메모는 읽지 않습니다.
- **같은 말은 같은 풀이로 풉니다.** 용어마다 기준 풀이가 하나 있습니다(`scripts/plain-language-rules.mjs`의
  `STANDARD_GLOSS`, 없으면 지금 가장 많이 쓰는 풀이). 사건마다 새로 풀다 보니 자문료는 아홉 가지, 심사
  엔진은 여덟 가지로 풀렸고, 실사는 사건 18에서 "사기 전에 장부와 서류를 샅샅이 확인하는 일", 사건 45에서
  "현장에 직접 가서 확인하는 일"로 뜻까지 달라졌습니다. 뜻이 다르면 낱말을 나눕니다: 실사는 현장, 사건 18의
  서류 확인은 "인수 실사"입니다. 기준과 다른 괄호는 경고이고 실패가 아니지만, 그 수는
  내려가기만 하는 천장이라 새 사건이 다른 문구를 쓰면 실패합니다. 목록은
  `node scripts/check-plain-language.mjs --glosses`로 봅니다. 기준 풀이가 마음에 들지 않으면 문장을 바꾸지 말고
  `STANDARD_GLOSS`를 고칩니다. 용어 바로 뒤의 괄호만 읽고, "발령서(…)"처럼 더 긴 낱말 뒤의 괄호는 읽지 않습니다.
- **한 문장에 괄호 풀이는 하나**입니다. 풀이가 둘 이상 필요하면 문장을 나눕니다. "계열사(…)와 부채비율(…)을
  보면 …"보다 "계열사(…)부터 봅니다. 그 회사의 부채비율(…)은 …"이 읽힙니다. 검사는 아직 이것을 세지 않습니다.
- 새 어려운 말을 썼다면 용어집에 더해 두면 검사가 다음부터 지켜 줍니다(README의 용어집 수도 함께 고칩니다).

### check:card-labels — 카드 라벨 길이

카드 라벨은 휴대폰에서 폭 약 165px 카드에 13px 글자 세 줄까지 보이고 그다음은 잘립니다. 그래서 라벨은
**30자 이하**로 씁니다. 세는 법: 앞뒤 공백을 빼고 공백 여러 개를 하나로 친 뒤, 한글·숫자·영문·공백·문장
부호를 모두 한 자씩 셉니다. 편집기에서 `"…".length`로 세는 값과 같습니다. 이미 30자를 넘는 옛 라벨이 있어서
검사는 "30자를 넘는 라벨의 수"와 "가장 긴 라벨의 길이"를 내려가기만 하는 천장으로 잡고 있습니다. 새 라벨이
30자를 넘으면 그 수가 올라가서 실패합니다. 기억 카드 문구(`memoryPlan`의 라벨)도 셉니다.

같은 검사가 **장면 본문(`text`)을 420자**까지로 봅니다. 세는 법은 라벨과 같고, `lead`는 세지 않습니다. 10월
22일에 420자를 넘는 본문이 133개(가장 긴 것은 사건 45 `c45_stories`의 702자)였고, 같은 날 문장 손질 뒤 115개·685자라서, 이것도 "420자를 넘는 본문의
수"와 "가장 긴 본문의 길이"를 내려가기만 하는 천장으로 잡습니다. 긴 본문은 장면을 나누거나, 숫자와 목록을
`memo`로 옮겨 줄입니다. 목록은 `node scripts/check-card-labels.mjs --texts`로 봅니다.

### check:fonts — 새 글자

게임 글꼴은 소스가 쓰는 글자만 잘라 만든 파일입니다. 새 문구에 지금까지 아무도 쓰지 않은 음절이 있으면 그
글자만 시스템 글꼴로 보입니다. 검사가 "Run `npm run build:fonts`"로 실패하면 `npm run build:fonts`를 돌리고,
바뀐 글꼴 파일과 글자 목록 파일을 **둘 다** 커밋합니다. 글꼴 파일 크기에는 내려가기만 하는 예산이 있습니다.
Pretendard에 없는 글자(한자 같은 것)는 검사 안의 예외 목록에 어디서 쓰는지 적어야 합니다.

### check:text — 깨진 글자와 조사

- 인코딩이 깨진 것처럼 보이는 문자열(�, 한글 사이의 이상한 한자 무리)이 있으면 실패합니다. Windows
  PowerShell은 멀쩡한 UTF-8 한글도 깨져 보이게 출력할 수 있으니, 화면만 보고 원고를 고치지 말고 이 검사와
  `check:encoding`을 기준으로 삼습니다.
- `${...}` 뒤에 "을/를", "이/가"를 박아 쓰면 안 됩니다. 숫자나 이름에 따라 조사가 바뀌기 때문입니다.
- 인물 이름과 회사 이름 뒤의 조사는 받침에 맞아야 합니다. "진태윤가"는 실패, "진태윤이"는 통과입니다.

### 판의 말은 이름 하나 — 물러난 말 (`npm test`)

판의 말은 하나에 이름 하나입니다(one-name-per-term). 물러난 말(푸시 → 밀기, 락 → LOCK, 차지 → 충전, 케이스 →
사건, 체인·연승 → 연속, 압박계 → 열기)은 `tests/unit/retired-terms.test.mjs`가 막습니다. 이 검사는 이야기
파일(`src/nodes/`)은 읽지 않습니다. 이야기 속에서 "연락", "차지하다"는 평범한 말이기 때문입니다. 대신 6장에서
고치는 **사건 둘레의 문구**(`src/gameCases.js`, `src/caseCopy.js`, `src/appCopy.js`)는 읽으므로, 사건 카드나
예고에 "케이스 50", "3연승" 같은 말을 쓰면 `npm test`에서 실패합니다.

### 그 밖에 같이 돌릴 것

- `npm run check:balance`: 늘 같은 쪽 카드만 골라도 모든 자원을 이기는 일이 없는지, 자원마다 오르기도 하고
  내리기도 하는지 봅니다. 라벨과 시간도 맞춰 봅니다.
  "바로", "즉시", "곧장"이라고 쓴 카드는 남은 시간을 잃으면 안 되고, "미룬다", "기다린다"로 끝나며 다른 일을
  하지 않는 카드도 시간을 잃으면 안 됩니다.
- `npm run check:endings`: 시즌 전체를 여러 방식으로 다시 플레이해, 써 둔 결말이 모두 나올 수 있고 어느
  하나가 기본 결말이 되지 않는지 봅니다. 새 사건의 숫자가 다른 사건과 너무 다르면 여기서 걸릴 수 있습니다.
- 단위 테스트와 브라우저 테스트(`season-flow` 등)는 시즌 전체를 사건 하나씩 걸어 봅니다.

## 8. 쓰고 나서 돌릴 순서

앞의 검사가 통과해야 뒤의 검사가 뜻 있는 말을 합니다. 그래프가 깨져 있으면 대사·쉬운 말 검사는 엉뚱한 장면을
읽기 때문입니다.

1. `npm run check:graph` — 사건 모양과 장면 잇기. 가장 먼저, 통과할 때까지 이것만 돌립니다.
2. `npm run check:canon` — 대출 사실과 요일이 붙은 날짜.
3. `npm run check:dialogue` — 연결·반응 장면의 대사가 자기 카드를 받는지. 사건을 더했다면 기대값부터 고칩니다(6장 7).
4. `npm run check:plain-language` — 쓰지 않는 말, 용어집 풀이.
5. `npm run check:card-labels` — 라벨 30자, 본문 420자.
6. `npm run check:text` — 깨진 글자, `${...}` 뒤 조사, 이름 뒤 조사.
7. `npm run check:fonts` — 새 음절. 실패하면 `npm run build:fonts`를 돌리고 다시 확인합니다.
8. `npm run check:balance`, `npm run check:endings` — 숫자. 둘 다 느리니 글이 다 정해진 뒤에 돌립니다.
9. 시즌에 올렸다면 `npm run check:doc-numbers`(README의 사건 수)와 `npm run check:grants`(서버의 사건 목록).
10. `npm run lint`, `npm test` — 물러난 말 검사도 여기 들어 있습니다.
11. 마지막으로 `npm run verify:static` 한 번. 위의 검사를 모두 나란히 돌리고, 실패한 것을 모아 보여 줍니다. 몇
    개만 고르려면 `npm run verify:static -- check:graph check:canon`처럼 이름을 붙입니다.

브라우저 테스트는 main에 병합된 뒤에 돕니다. 그 전에 위 순서를 모두 통과시켜 둡니다.

## 10. 글 방향: 한국 직장의 블랙 코미디

이 게임의 웃음은 한국 직장과 금융의 부조리에서 나옵니다. 새 사건이나 카드 문구를 쓸 때 이 방향을 기준으로
삼습니다. 지금 사건들도 이미 이쪽에 있습니다. 강서지점 입구의 실적판과 그대로 붙은 "이달의 판매왕"
스티커(사건 07), 대표이사와 CFO가 작은아버지와 고모부인 회사(사건 09), 33층에 올라가는 날 "왕복 교통비
견적"을 보내는 동료(사건 49)가 그 예입니다.

**쓸 만한 소재**

- 낙하산: 회장 조카가 본부장으로 오는 날, 그 사람의 첫 지시가 "보고서 글꼴 통일"인 아침.
- 실적 압박 메시지: 부장이 새벽 1시에 단체방에 올리는 "다들 자나? 내일 9시까지 실적 공유 부탁 ^^", 웃는 얼굴
  이모티콘 뒤의 숫자 목표.
- 숫자 맞추기: 보고서에 맞춰 바뀌는 숫자, 회의를 위한 사전 회의, 승인 라인에 이름만 남은 사람.
- 책임이 내려가는 길: 위에서 정한 일을 창구 직원의 이름으로 남기는 공문.

**쓰는 법**

- 웃음의 과녁은 제도와 권력입니다. 피해를 본 사람(창구 직원, 야간조, 대출을 받은 소상공인)을 웃음거리로
  삼지 않습니다.
- 우스운 장면과 대가를 한 장면에 둡니다. 사건 49의 여파처럼 컵라면 두 개와 명세서의 "흑자"가 나오는 같은
  장면에서 그 밤이 마지막일 수 있다는 무게가 함께 갑니다. 카드의 `echo`는 웃긴 첫 문장 뒤에 치르는 것을
  한 줄 남기면 좋습니다.
- **감정 넷은 사건마다가 아니라 막 단위로 맞춥니다.** 분노·웃음·슬픔·기쁨을 사건 하나에 모두 넣으면 20장면이
  늘 같은 배합으로 돌아갑니다. 넷은 막(README의 0~8막) 안에서 고루 가면 되고, **막마다 한 감정만 가는 사건을
  하나 둡니다.** 예를 들어 웃음 없이 슬픔만 가는 사건, 분노 하나로 끝까지 가는 사건입니다. 새 사건을 쓰기 전에
  같은 막의 사건들이 어느 감정에 기대고 있는지(사건 파일 첫 주석)를 읽고 고릅니다. 지금 정해 둔 한 감정 사건은
  1막 05(분노), 2막 10(소진), 4막 21(고요한 슬픔), 6막 32(웃음 없이 분노·두려움)이고, 사건 파일 첫 주석에
  「Act N's one-emotion case」로 적혀 있습니다. 이 사건들에는 웃음을 더하지 않습니다.
- 농담은 인물이 합니다. 내레이션이 플레이어에게 윙크하지 않고, 인물이 자기 말투대로 진지하게 우스운 말을
  합니다(인물의 말투는 `characterProfiles`의 `voice`, `line`에 있습니다).
- 직장 은어도 어려운 말입니다. "낙하산", "대기발령" 같은 말은 처음 읽히는 곳에서 괄호로 풉니다. 용어집에
  없으면 더해 둡니다(7장 check:plain-language).
- 이름과 직함으로 함께 불리는 사람은 장면마다 내레이션이 처음 부를 때 둘을 붙여 쓰고(「서도경 회장」,
  「나준혁 지점장」), 그다음부터는 직함만 씁니다(「회장」). 장면은 `lead`, `text`, `question` 순서로 읽힙니다.
  인물이 말하는 따옴표 안(「회장님」)은 그 사람 말투대로 둡니다.

**지킬 것**

- **실존 인물과 실존 기업은 쓰지 않습니다.** 정치인, 기업인, 연예인, 실제 은행·증권사·그룹의 이름을 쓰지
  않고, 실제 사건을 알아볼 수 있게 옮겨 오지도 않습니다. 회사와 은행은 시즌의 가상 이름(KD금융그룹, KD은행,
  KD캐피탈, 플로우온 같은 것)을 쓰고, 새 회사 이름은 지금 들어도 어색하지 않되 실제로 없는 이름을 지은 뒤
  검색해서 확인합니다. 금융감독원, 국정감사, 부제소 합의처럼 제도와 기관의 일반 이름은 씁니다.
- **canon을 지킵니다.** 대출 2023-0412의 사실은 `docs/canon.md`의 값만 쓰고, 메시지에 날짜와 요일을 박을
  때는 연도 표(7장 check:canon)를 봅니다. 새벽 단체방 메시지도 사건의 해 달력에 맞는 요일이어야 합니다.
- 우스운 숫자도 숫자입니다. 메모에 적은 금액·인원·시각은 같은 사건의 다른 장면과 맞아야 합니다.

**판 화면의 목소리 (A-16)**

판(테이블) 위의 말은 해라체로 씁니다. 열기·벽·판돈·판정 원인·다음 판의 규칙처럼 판이 스스로 말하는 줄입니다
(「판돈 1,200을 잃었다.」「벽은 64에 있었다.」「다음 판이 이렇게 부서진다」). 결정 공개 시트에서 판 밖의 일을
플레이어에게 알리는 줄은 합니다체로 씁니다. 도구가 도감에 들어간 것, 사건이 닫혀 드래프트가 열리는 것,
당신 없이 넘어간 장면처럼 이야기와 기록 쪽의 소식입니다(「도감에 들어갔습니다.」「사건이 닫혔습니다.」
「위험관리부는 당신 없이 「…」를 넘겼습니다.」). 장면 본문과 카드의 `echo`는 지금처럼 합니다체입니다. 새 줄을 더할 때는
그 줄이 판의 숫자를 읽는 줄인지, 판 밖의 소식을 전하는 줄인지로 고릅니다.
