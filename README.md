## 무엇을 위한 게임인가

원래 질문은 저장소 이름 그대로입니다: **"내 창의성은 언제 가장 크게 확장되는가."** 임계점은 그 질문을
플레이로 바꾼 실험입니다. 사람의 판단은 압박이 전혀 없을 때도, 압박에 짓눌릴 때도 얕아집니다.
그 사이 어딘가 — 판돈이 커지고 시계가 줄어드는데도 아직 생각할 여유가 남아 있는 구간 — 에서
생각이 가장 깊어진다는 가설을, 플레이어가 직접 밀어붙이고 멈추는 행동으로 측정합니다.

- **플레이어에게는** 정답 없는 기업·금융 위기 쉰다섯 건을 지나며 "나는 어디까지 밀고, 무엇을
  먼저 지키는 사람인가"를 확인하는 판단 스릴러입니다. 선택은 사건을 끝내지 않고 다음 판의 규칙을
  바꾸므로, 한 시즌이 끝나면 자기 판단 습관이 결말과 리포트로 남습니다.
- **만든 사람에게는** 플레이테스트 도구입니다. 어떤 조건에서 즉답 대신 근거를 찾고, 선택지 밖의
  문장을 쓰고, 무너진 뒤 회복하는지를 익명 텔레메트리(동의한 경우에만)로 모읍니다. 이야기의
  마지막 사건은 이 구조 자체 — 생각을 깨우는 조건은 조종 가능한 조건이기도 하다 — 를 되묻습니다.

질문을 한 줄로 줄이면 **"나는 얼마나 똑똑한가"가 아니라 "나는 언제 똑똑해지는가"** 입니다. 이 게임의
가설은 강한 감정이 지성을 방해하는 것이 아니라 방향을 정한다는 것입니다.

> 감정의 방아쇠 → 집념 → 멈추지 않는 생각 → 지성 → 자본과 조직을 움직임 → 현실의 변화

애정은 사람을 살리는 쪽으로(구제), 복수심은 약점을 찾는 쪽으로(교정), 책임은 장부를 맞추는
쪽으로(회생) 같은 집념을 겨눕니다. 사건 08과 09가 이 셋을 정면으로 다루고, 사건 10은 그 집념이
소모되는 속도를 잽니다. 리포트의 `판단 DNA`는
이번 판에서 가장 오래 남은 트리거 묶음을 **생각이 깨어나는 조건**(애정형·복수형·책임형·탐구형)으로
이름 붙여 돌려줍니다.

## 어떻게 플레이해야 하나 (전략)

점수는 두 층입니다. **테이블**에서는 칩을 금고로 옮기는 푸시 유어 럭을 하고, **사건 리포트**에서는
그 과정이 얼마나 깊은 판단이었는지를 0~100의 버스트 점수로 매깁니다. 둘은 서로를 끌어당깁니다.

**테이블에서 살아남기**

- **금고가 유일한 안전지대입니다.** 벽은 이번 사건 판돈만 가져가고 금고는 못 건드립니다. 크게
  한 번 터뜨리기보다 여러 번 챙기는 쪽이 시즌 전체로는 강합니다.
- **심박을 읽으십시오.** 벽의 위치는 끝까지 나오지 않고, 심박이 빨라질수록 벽이 가깝다는 신호입니다.
  다만 오차가 있으니 벽 구간에 들어서면 한 번 더 미는 것 자체가 도박입니다.
- **박자에 맞춰 미십시오.** PERFECT/GOOD 콤보가 판돈에 GROOVE를 붙이지만(박자와 LOCK을 합친 상한 ×1.5), 박자를 놓치면
  콤보가 끊기고 시계 1초를 잃습니다. 박자는 벽을 옮기지 않으므로 "박자가 좋으니 한 번 더"는 함정입니다.
- **다음 판을 생각하고 확정하십시오.** 한 번도 밀지 않고 확정하면 가장 좋은 카드가 봉인되고(COLD FEET),
  너무 높은 배율로 확정하면 열기와 시간을 빚집니다(HEAT DEBT). 방금 가장 크게 태운 자원은 다음 판에서
  1.5배로 청구되니(FRACTURE) 같은 자원만 계속 태우지 마십시오. 시간 초과는 심박을 없앱니다(SILENCE).
- **시즌은 뒤로 갈수록 조입니다.** 판 100개마다 벽이 그려지는 구간의 위쪽 끝이 2씩 내려오고 시계가 열기를
  조금 더 빨리 올립니다(최대 네 단계, 구간의 아래쪽 끝은 움직이지 않음). 뒤쪽 사건일수록 지침이 조금
  쌓이고 남은 시간이 조금 줄어든 채로 시작하므로(마지막 사건에서 지침 +14, 시간 −8), 초반에 금고를
  쌓아 두는 편이 후반을 버티기 쉽습니다.
- **도구는 약점을 메우는 쪽으로 고르십시오.** 자주 터진다면 냉혈·방열판, 박자가 어렵다면 메트로놈처럼,
  드래프트 세 장 중 지금 시즌의 생각 방식에 맞는 것을 고르는 편이 수치가 큰 것보다 낫습니다.

**높은 버스트 점수를 받기**

버스트 점수는 테이블 금고가 아니라 판단의 결을 봅니다. 결과 화면의 점수 칸과 같은 항목이며, 비중은 다음과 같습니다.

| 항목 | 비중 | 올리는 법 |
|---|---|---|
| 기준 유지 | 28% | 압박이 올라간 장면에서도 앞서 지킨 방향을 뒤집지 않는다 |
| 관점 전환 | 20% | 추론·위험 회피·재구성·버티기를 한 가지로만 반복하지 않는다 |
| 구조 재설계 | 20% | `판을 다시 짠다`로 사건의 숨은 경로를 열고, 숨은 기록을 찾는다 |
| 압박 대응 | 16% | 위험을 무조건 피하기보다, 치솟은 압박을 다음 장면에서 회수한다 |
| 생각 리듬 | 8% | 즉답도 방치도 아닌, 읽고 결론까지 밀어낸 시간대에 누른다 |
| 장면 챌린지 | 8% | 장면마다 걸린 챌린지 조건을 맞추고, 연속으로 이어간다 |
| 즉답 패널티 | 최대 −18 | 판을 다시 짜지 않고 2초 이내로 누르는 선택 한 번마다 −5 |

S(88+)·A(72+)·B(52+)·C 랭크가 여기서 나옵니다. 요약하면 **빨리 누르는 사람이 아니라, 흔들리는
판에서 자기 기준을 지키면서도 판 자체를 다시 짜는 사람**이 높은 점수를 받습니다.

결말은 마지막 사건의 숫자 하나가 아니라 **시즌 전체의 평균과 비율**을 읽습니다. 자원(남은 시간, 현금,
믿음, 공정함, 사람 피해, 지침)은 사건마다 닫힐 때의 값을 평균하고, 찾은 기록은 플레이한 사건 수에 대한
비율로 셉니다. 사건당 평균 사람 피해가 20 이상이거나, 10 이상인 채 판의 20% 이상을 터뜨렸다면
SYSTEM COLLAPSE입니다. 최고 열기가 아니라 피해와 무리수가 무너짐을 정합니다. 마지막 사건에서 기록을
태우면 기록으로 여는 세 결말(OPEN OVERSIGHT, EVIDENCE REFORM, HUMAN RECORD)이 닫힙니다. 결과 화면의
실패 조언과 시즌 목표는 같은 기준값(`ENDING_GATES`)을 인용합니다.

시즌이 끝나 기록이 열리는 화면에서는 `결과 카드 저장`으로(사진을 공유할 수 있는 기기에서는 `결과 카드
공유`로도) 판단 DNA, 결말, 시즌 최고 버스트 점수와 랭크, 리그를 담은 1080×1350 그림 한 장을 받습니다.
카드에도, 함께 복사되는 한 줄에도 이름, 남긴 말, 세션 코드는 들어가지 않습니다.

## 무엇으로 경쟁하나

- **랭킹 보드** — 완료한 사건의 버스트 점수(0~100)로 순위를 매깁니다. 동점이면 랭크 → 구조 재설계
  → 압박 대응 → 관점 전환 순으로 가립니다. 한 런(run)은 가장 좋은 기록 하나만 오르고, 시즌을 끝낸
  기록이 중간 기록보다 항상 앞섭니다. 같은 런을 여러 번 제출해도 순위를 도배할 수 없습니다.
  시즌 길이가 바뀔 때마다 공개 랭킹과 로컬 랭킹을 모두 비우고 새로 쌓습니다. 공개 랭킹은 서버 검증
  규칙을 강화한 2026-09-28 마이그레이션에서 새 규칙을 통과하지 못하는 시즌 기록을 지우므로, 배포 직후
  사실상 다시 쌓입니다.
- **리그** — 플레이 스타일로 나뉩니다. 판을 다시 짜 온 **REFRAME LEAGUE**(BOARD BREAKER),
  압박 회수가 두드러진 **RISK LEAGUE**(RISK CUTTER), 구조적 생각이 높은 **SYSTEM LEAGUE**(SYSTEM
  THINKER), 현장 판단형 **FIELD LEAGUE**(FIELD DECIDER). 같은 점수라도 어떤 방식으로 도달했는지가 함께
  표시됩니다.
- **로컬과 원격** — 서버가 없으면 이 브라우저의 기록끼리 겨루는 로컬 보드가, Supabase가 설정되어
  있으면 공개 보드가 뜹니다. 공개 보드의 다른 참가자는 이름 없이(모두 '익명 분석관') 스타일과 런
  태그(`run_tag`, 런 ID의 끝 여덟 글자)로만 보이고, 순서는 서버가 계산한 점수로 정합니다. 서버는 그
  런이 시즌의 모든 사건 기록을 이미 남겼고 첫 기록이 10분 이상 지났을 때만 시즌 기록을 받으며, 런
  하나에 한 줄, 세션 하나에 하루 두 줄까지입니다. 랭킹의 `RUN LINKED` 배지는 기록이 런 ID에
  묶였다는 뜻이지 서버가 검증했다는 뜻이 아닙니다 — 공개 랭킹은 플레이테스트 순위이지 부정행위 방지
  장치가 아닙니다.
- **자기 자신과의 경쟁** — 시즌 로드맵, 도구 도감(시즌을 리셋해도 남음), 9가지 결말, NEW GAME+가
  재도전 동기입니다. 결과 화면의 `이 사건 다시 도전`(`R`)은 같은 사건을 다른 기준으로 다시 밀어볼
  때 씁니다. 다시 도전한 판은 그 사건의 요약(결말이 읽는 값)을 새 판의 것으로 바꾸지만 연습으로 셉니다:
  금고와 테이블 기록은 그대로이고, 시즌이 조여지는 단계를 올리지 않으며, 로컬 랭킹에는 줄이 더해지지 않고
  그 사건의 줄이 바뀝니다. 시즌 전체를 지우는 버튼은 `시즌 처음부터 다시`로 따로 있고 색으로 구분됩니다.

### 참가자 게시판

랭킹은 점수만 보여 주고, 결말 뒤의 '다음 참가자에게 남기는 말'은 이 브라우저에만 남습니다.
게시판은 그 사이입니다 — **닉네임 하나만 정하면 300자까지 짧은 글**을 남길 수 있고, 다른 참가자가
읽습니다. 로그인도 이메일도 없습니다.

이 게임에서 사람이 쓴 글이 **이름과 함께 공개되는 유일한 자리**이기도 해서(랭킹의 다른 참가자는
전부 '익명 분석관'입니다), 자동 등록은 서버에서 여섯 겹으로 막습니다. 속도와 반복 검사는 보내는
주소(서버가 믿을 수 있는 경로로 확인한 IP) 기준이고, 같은 주소의 글은 잠금 아래에서 하나씩 판정하므로
동시에 여러 번 보내도 규칙을 건너뛸 수 없습니다.

| 막는 것 | 방식 |
|---|---|
| 형태 | 닉네임 2~24자, 글 2~300자. 눈에 보이는 글자가 두 자 이상이어야 하며, 앞뒤의 유니코드 공백·보이지 않는 문자는 지웁니다 |
| 링크 | 본문이나 닉네임에 링크가 있으면 거절합니다. 도메인만 쓴 주소, `[.]`·`(dot)`·전각 점·`닷컴` 같은 우회 표기도 잡습니다 |
| 연락처 | 전화번호(휴대폰·유선·+82)와 이메일 주소는 서버에서도 거절합니다 |
| 속도 | 한 기기(세션)는 30초에 한 번·한 시간에 열 번, 한 주소 전체는 30초에 세 번·한 시간에 서른 번까지. 교실처럼 주소 하나를 여럿이 쓰는 경우 때문에 두 단계입니다 |
| 반복 | 같은 주소에서 6시간 안에 같은 글을 다시 보내면 성공으로 응답하고 저장하지 않습니다 |
| 재전송 | 같은 글이 두 번 전송돼도 한 번만 저장됩니다 |

화면 쪽에도 사람이 왕복 전에 알 수 있도록 같은 규칙을 걸어 두었고, 봇만 채우는 숨은 입력칸과
'연 지 3초 안에 제출'을 막는 장치가 더 있습니다. 실명·연락처·회사명이 보이면 제출을 막고
익명화 버튼을 띄웁니다(회사명 검사는 화면에서만 합니다). 서버가 없는 배포에서는 화면은 열리되 글을
주고받을 수 없다고 알립니다. 글을 숨기거나 되살리는 것은 서비스 롤로만 실행되는
`moderate_board_post(id, hidden)`로 합니다.

## 개발 환경

Node는 `.node-version` 한 곳에서 정합니다(지금 24.20.0, `package.json`의 `engines.node`는 `>=24 <25`).
CI와 Render 빌드가 같은 파일을 읽으므로 로컬도 fnm이나 nvm으로 그 버전을 씁니다.

```bash
fnm use                                        # fnm은 .node-version을 직접 읽습니다
# nvm이라면: nvm install "$(cat .node-version)" && nvm use "$(cat .node-version)"
npm ci
npx playwright install chromium   # e2e·런타임 스모크·시각 회귀에 필요
cp .env.example .env.local        # 선택: Supabase를 쓸 때만
npm run dev
```

브라우저에서 터미널이 알려주는 `http://127.0.0.1:<port>`를 엽니다.

`.env.local`에 넣는 값은 셋입니다. `VITE_SUPABASE_URL`과 `VITE_SUPABASE_ANON_KEY`(없으면 원격 랭킹·
텔레메트리·게시판·온라인 저장이 꺼진 채로 동작합니다), 그리고 `VITE_ENABLE_DEBUG_TOOLS`(디버그 패널,
기본 `false`). 서비스 롤 키는 여기에 넣지 않습니다.

자주 쓰는 명령:

```bash
npm run verify:static   # 브라우저 없는 검사 25개를 병렬로 (~40초)
npm run verify:quick    # + 프로덕션 빌드, 번들 예산, 빌드 위 런타임 스모크와 @prod e2e
npm run verify          # + 기본 e2e와 성능 예산
npm run test:coverage   # 단위·스모크 테스트 커버리지 (로직 모듈 합계 줄 88%·함수 87%·분기 76%, 모듈마다 하한)
npm run check:types     # jsconfig.json에 올린 순수 모듈만 tsc로 검사
npm run test:e2e:season # 시즌 전체를 끊지 않고 한 번에 걷기 (주간 Full Coverage가 도는 것)
```

시각 회귀 베이스라인은 리눅스 컨테이너에서만 기록합니다. Docker가 있으면
`npm run test:visual:docker -- --update-snapshots`로 로컬에서, 없으면 GitHub Actions의 `Visual Regression`을
`update_baselines=true`로 수동 실행한 뒤 그 실행이 올린 `visual-baselines/<run_id>` 브랜치를 병합합니다.
Windows·macOS에서 찍힌 베이스라인은 무시(gitignore)되고 커밋하면 `check:visual-baselines`가 거절합니다.

PR에서 무거운 검사는 라벨로 켭니다. `e2e` 라벨은 e2e 티어를, `visual` 라벨은 시각 회귀를 돌립니다.
Dependabot PR은 라벨 없이도 e2e와 시각 회귀를 모두 돕니다(의존성 업데이트가 게임을 깨뜨리기 가장 쉬운 변경이라서).
저장소의 텍스트 파일은 모든 플랫폼에서 LF로 체크아웃됩니다(`.gitattributes`, `.editorconfig`). 바이트로
재는 예산이 Windows에서 CRLF를 재던 문제 때문입니다.

## 게임

- **브리핑 페이지** — 장면이 열리면 테이블 앞에 그래픽 노블 한 페이지가 크게 펼쳐집니다. 방 그림
  위에 장소·마감 캡션과 효과음이 박힌 스플래시 컷, 화자의 초상과 그 장면의 질문이 담긴 말풍선,
  경위와 본문을 한 문장씩 나눈 캡션 박스, 핀으로 꽂힌 `사건 파일` 메모가 한 장에 들어가고, 직전
  판단이 판을 부쉈다면 바뀐 규칙(PROTOCOL BREACH)이 붉은 컷으로 붙습니다
  (`src/gauntlet/SceneBriefing.jsx`, `src/styles/app/briefing.css`).
  이 페이지에는 **읽는 시간 제한**이 따로 있습니다. 본문 길이에 맞춰 12~50초
  (`getReadingSeconds`)이고, 다 되면 판이 저절로 열립니다. 남은 초를 보여 주는 시계는 버튼이라, 누르면
  읽는 시간이 멈추고 다시 누르면 흐릅니다. 그 전에 언제든 `판 열기`(`Space`/`Enter`)로
  열 수 있고, 페이지 아래의 카드 버튼(또는 숫자 키)을 누르면 **그 카드를 건 채로** 판이 열립니다.
  페이지가 떠 있는 동안 테이블의 45초는 멈춰 있으므로, 리포트의 `생각 리듬`은 읽는 시간이 아니라
  판단한 시간만 잽니다.
- **테이블** — 한 장면이 한 화면입니다. 위에서부터 판돈(칩 × 배율), 열기 게이지와 벽이 그려진
  구간, 장면의 질문, 카드 패, 그리고 `밀어붙인다` / `확정` 두 버튼. 390x844 휴대폰, Pixel 7,
  1280x720 데스크톱, 1366x768 노트북에서는 모든 장면이 규칙이 쌓인 판에서도 스크롤 없이 카드가
  액션 바 위에 들어갑니다. 넓은 화면은 왼쪽에 읽을 것, 오른쪽에 카드 패를 두는 두 칸 배치입니다.
  옆으로 누인 휴대폰(높이 480px 이하의 가로 화면)에도 전용 배치가 있어서, 640x360부터 932x430까지 카드
  다섯 장이 스크롤 없이 들어옵니다(`src/styles/app/responsive.css`). 고정된 층은 좌우 안전 영역도 비웁니다.
- **단계별 해금** — 테이블의 규칙은 처음부터 전부 켜져 있지 않습니다. 프롤로그 다섯 장에 걸쳐 한
  단계씩 열리고, 사건 01부터는 전부 켜져 있습니다(`src/gauntlet/tableUnlocks.js`).

  | 사건 | 새로 열리는 것 |
  |---|---|
  | 프롤로그 01 | 밀어붙이기·확정·벽·심박 (테이블 자체) |
  | 프롤로그 02 | 박자와 콤보, BLACKOUT·AFTERSHOCK·SILENCE |
  | 프롤로그 03 | COLD FEET, HEAT DEBT |
  | 프롤로그 04 | FRACTURE, OVERCLOCK, LOCK (자세는 STRIKE로 고정) |
  | 프롤로그 05 | 자세 선택, 도구 드래프트 (프롤로그 04가 닫힐 때의 제안부터) |

  아직 열리지 않은 규칙은 화면에 그려지지 않고 키도 받지 않습니다. 박자 고리와 판정, LOCK 버튼과 `E`,
  자세 줄과 `Q`가 그 단계 전에는 없습니다. 규칙이 열리는 사건의 첫 브리핑 페이지에는 새 규칙을 한두
  줄로 알리는 컷(NEW PROTOCOL, 프롤로그 01은 FIRST TABLE)이 화자와 질문 바로 아래에 붙어서, 스크롤하지
  않아도 첫 화면에서 질문과 함께 보입니다(PROTOCOL BREACH 컷은 그대로 페이지 맨 아래). 프롤로그 01에서도 벽에 닿으면 판돈을 잃고 다음 장면을
  건너뛰지만, 다음 판의 규칙은 바뀌지 않습니다. NEW GAME+로 시작한 회차는 프롤로그 01부터 전부 켜져
  있고 소개 컷이 없습니다. 닫은 프롤로그를 다시 하면 그 사건의 단계로 플레이합니다. 단계가 생기기 전에
  프롤로그 중간에서 저장한 회차는 가진 도구와 판을 그대로 두고, 다음 판부터 새 단계를 따릅니다.
- **카드** — 선택지 하나가 카드 한 장입니다. 카드는 칩(이득)과 가장 크게 태우는 자원만 보여줍니다.
  `판을 다시 짠다`는 모든 장면에 한 장씩 있는 와일드 카드입니다. 이 카드를 확정하면 사건마다
  하나씩 숨어 있는 경로가 열리고, 거기서 다시 세 개의 선택지를 만납니다. 사건당 한 번만 열리고,
  터지면 열리지 않습니다.
- **밀어붙이기** — 누를 때마다 열기가 7~15 오르고 배율은 열기 11마다 두 배가 됩니다. 벽은
  표시된 구간 어딘가에 있고 정확한 위치와 확률은 나오지 않습니다. 심박만이 벽을 가리키는
  계기이며, 그마저 오차가 있습니다. 가만히 있어도 시계가 열기를 올리고, 시간이 끝나면 터집니다.
- **박자** (프롤로그 02부터) — 심박이 곧 테이블의 리듬입니다. 밀어붙이기 버튼 위의 고리가 다음 심박에 맞춰 닫히고,
  박자에 맞춰 누르면 PERFECT/GOOD 콤보가 쌓여 판돈에 GROOVE 보너스가 붙습니다(LOCK과 합친 상한 ×1.5, `HAND_CAP`). 박자를
  놓치면(SLIP) 콤보가 끊기고 시계 1초를 잃습니다. 박자는 벽의 위치나 열기 폭을 바꾸지 않습니다.
  확정하면 콤보가 다음 판으로 이어지고, BUST는 판돈과 함께 콤보도 가져갑니다.
- **도구 드래프트** (프롤로그 04가 닫힐 때부터) — 사건이 닫히면 다음 사건의 첫 테이블에서 도구 3개 중 하나를 고릅니다(`1`~`3`,
  `Esc`는 건너뛰기). 도구는 시즌이 끝날 때까지 규칙 하나를 바꿉니다: 여진을 식히는 냉혈, 열 빚을
  줄이는 방열판, 봉인을 일찍 여는 락픽, 균열 청구를 줄이는 부목, 박자 판정을 넓히는 메트로놈. 콤보 8,
  판돈 5,000 이상의 BUST, ×64 확정, SILENCE 같은 위업은 앙코르·보험·하이롤러·청진기를, 자세마다
  숙련 3회(STRIKE·STEADY·EXPOSE)는 악력·닻·돋보기를 도감에 해금하고, 도감은 시즌을 리셋해도 남습니다.
  드래프트가 떠 있는 동안 시계는 멈추고, 키보드 초점은 드래프트 안에 머물다 닫히면 원래 자리로
  돌아갑니다(브리핑 페이지도 같습니다).
- **BUST** — 벽에 닿으면 이번 사건에 걸린 판돈이 0이 되고, 카드는 이득 없이 비용만 치릅니다.
  카드를 고르지 않았다면 회의실이 가장 비싼 카드를 대신 고릅니다. 사건이 닫힐 때 판돈은 금고로
  옮겨지고, 금고는 벽이 가져가지 못합니다.
- **다음 판의 붕괴** — 모든 결정이 다음 판의 규칙을 바꿉니다. BUST 후엔 카드가 뒤집히고 벽이
  가까워지며 열기가 22에서 시작합니다(BLACKOUT, AFTERSHOCK). 시간 초과는 심박을 없애고 시간을
  30초로 줄입니다(SILENCE). 높은 배율로 확정하면 열기와 시간을 빚지고(HEAT DEBT), 한 번도 밀지
  않고 확정하면 가장 좋은 카드가 봉인됩니다(COLD FEET). 연속으로 크게 챙기면 칩과 열기가 함께
  커지고(OVERCLOCK), 방금 가장 크게 태운 자원은 다음 판에서 1.5배로 청구됩니다(FRACTURE). 프롤로그에서는
  그 단계에 열린 규칙만 다음 판을 바꿉니다.
- **자원과 결말** — 남은 시간, 현금, 믿음, 공정함, 사람 피해, 지침은 여전히 이야기의 축이고, 결말은
  시즌 내내 사건이 닫힌 값의 평균과 BUST 비율을 함께 읽습니다. 리포트의 `테이블 장부`가 금고, 최고 배율, BUST, 잃은
  판돈을 보여줍니다.

- **이야기와 좌표** — 장면마다 어느 건물의 어느 방인지와 마감까지 남은 시간이 화자 위에 한 줄로
  붙고, 카드 위의 질문은 그 장면이 실제로 묻는 것을 말합니다. 라우트가 갈리면 장면은 쓰인 순서대로
  재생되지 않으므로, 모든 장면은 앞 장면에 기대지 않고 스스로를 설명합니다(`src/nodes/sceneContext.js`).
  판이 열린 뒤에도 테이블의 접힌 `사건 브리핑`에서 경위와 사건 팩트를 다시 볼 수 있습니다.
- **장면 그림** — 시즌의 모든 장면이 자기 방 그림을 가집니다. 파일로 싣는 대신 장면이 이미
  말하고 있는 `place`와 `phase`에서 그려내므로(`src/scenePlate.js`), 내려받을 바이트가 없고
  장면을 다른 건물로 고쳐 써도 그림이 따라옵니다. 옥상·거리·택시 뒷자리·물류 현장·통제실·서고·
  로비·복도·회의장·국정감사장·편집국·시장 떡집·추모공원·멈춘 공장·광고 스튜디오·주주총회 대강당·서버실·제주 감귤밭·트레이딩룸·수능 교문·공사 현장·법정·공항·콜센터·은행 창구·바닷가·갤러리·헌책방·새벽 카페·병실·책상 서른한 가지 방이 있고,
  **방마다 사람이 들어 있습니다** -- 화자가 서 있을 자리에
  실루엣이 놓이므로 도면이 아니라 장면으로 읽힙니다. 빛의 색은 **그 방을 소유한 조직**이 정합니다.
  트리거랩, 플로우온, KD은행, 온새, 경쟁 은행, 그리고 국회와 언론이 각자 다른 색으로 켜지고, 아무도 고용하지 않는
  곳 -- 헌책방, 시장, 바닷가, 병실, 카페 -- 만 따뜻한 흰빛을 씁니다. 그래서 시즌이 어디로 이동했는지,
  그리고 지금 누구의 건물 안에 서 있는지가 날짜 줄을 읽기 전에 보입니다. 한 조직의 방은 몇 개든
  같은 색이므로, 트리거랩 4층과 지하 보관소와 옥상은 같은 건물로 읽힙니다.
  화자 줄 뒤에 깔리고, 브리핑 페이지의 스플래시 컷과 접힌 `사건 브리핑`에서는 또렷한 판으로 나옵니다. 그림은
  멈춰 있지 않습니다. 먼 배경이 천천히 흐르고, 방의 핵심 불빛이 숨 쉬듯 깜빡이며, 낮에는 먼지가,
  자정 넘은 바깥에는 비가 내립니다. 택시와 새벽 카페처럼 유리가 대부분인 방에서는 그 비가 창밖으로
  흘러갑니다. 화면이 많은 방에는 주사선이 지나가고, 압박이 걸린 장면은 붉은
  테두리가 맥박처럼 뛰며, 브리핑 속 그림은 아주 느리게 다가옵니다. 그 위에 효과층이 한 겹 더 있습니다.
  국정감사장과 편집국처럼 모두가 지켜보는 방에서는 카메라 플래시가 터지고, 하늘이 트인 곳과 높은 창으로
  빛이 드는 공장·추모공원의 낮에는 빛줄기가 비스듬히 흔들리며, 떡집과 카페에서는 김이 피어오르고, 압박이 걸린 밤의 바깥에는 번개가 두 번씩 칩니다. 두 번째 효과층도 있습니다. 시계가 겨울(12·1·2월,
  첫눈, 한파)을 가리키면 하늘이 트인 곳과 유리창 너머에 비 대신 눈이 내리고, 스튜디오와 대강당은 천장의 조명이
  무대를 훑고, 서버실과 트레이딩룸은 LED가 깜빡이고 시세판이 흐르며, 밤의 도시는 초점이 나간 빛망울로
  번집니다. 근경은 원경과 반대로 아주 조금 흔들려 깊이가 생기고, 장면을 움직이는 감정(첫 트리거)이
  색으로 한 겹 깔립니다 -- 사람에 관한 장면은 따뜻하게, 부당함에 관한 장면은 뜨겁게, 두려움에 관한 장면은
  차갑게. 브리핑 속 그림에는 창문 빛이 종이에 스치듯 빛 번짐이 천천히 지나갑니다. 세 번째 효과층은 두 번째 해의 계절입니다.
  4월의 벚꽃잎, 7월 장마의 굵은 비와 물웅덩이에 번지는 동그라미, 8월 폭염의 아지랑이, 축제 밤의 불꽃, 9월의 낙엽,
  그리고 추석 밤하늘의 보름달이 장면의 시계에서 읽혀 나옵니다(`src/styles/app/plate.css`). 모든 그림에는 인쇄물 같은
  필름 그레인이 깔리고, 직전 판단이 판을 부순 장면은 브리핑의 스플래시 컷이 붉은색과 청록색으로 갈라지는
  글리치와 함께 열립니다. 모든 움직임은 장면 id로 정해져 같은 장면은 늘 같은 모습이고, 모션 줄이기
  설정에서는 플래시·번개·김·글리치를 빼고 완성된 정지 그림으로 멈춥니다.
- **초상** — 초상화가 있는 다섯 명(한서윤, 반재욱, 도윤하, 오진우, 에코) 말고는 전부 같은 사진 한 장으로
  대신하던 것을 없앴습니다. 초상화가 없는 인물은 이름에서 정해지는 색으로 역광을 받은 실루엣과 이름 첫
  글자로 그려지므로(`src/components/SpeakerPortrait.jsx`), 나준혁과 서하린이 같은 얼굴로 나오지 않습니다.
- **막간** — 사건이 닫히면 리포트에 베팅도 시계도 선택도 없는 장면이 하나 붙습니다. 컵라면, 문자
  한 통, 자판기 앞의 안 웃긴 농담, 같은 가자미 사진 서른 장, 계산으로 정한 축가 부탁, 명예 기자증을
  받은 편집국 고양이, 고등학생이 지어 온 공장 이름 '끝까지정밀' 같은 것들입니다. 쉰다섯 개의 사건이 같은 톤으로 이어지지 않게 하는
  자리이고, 사건이 다루지 못하는 인물의 뒷이야기가 여기서 이어집니다. 누군가 떠나는 사건(06, 16, 18)의 막간은
  장면이 아니라 날짜가 붙은 기록이고, 그 안의 '당신이 고른 것' 줄은 플레이어가 고른 카드의 이름을 적습니다(판단 기록에 남는 바로 그 카드입니다).

### 키보드

| 키 | 동작 |
|---|---|
| 숫자 키 | 카드 걸기 (브리핑 페이지에서는 그 카드를 걸고 판 열기, 드래프트 중에는 도구 고르기) |
| `Esc` | (드래프트) 도구 없이 진행 |
| `Space` / `W` | (브리핑 페이지) 판 열기 · (판) 밀어붙인다 |
| `Enter` | (판) 확정 · (브리핑 페이지) 판 열기 · (드래프트) 초점이 놓인 도구 고르기 |
| `E` | (판) 초점 고정(LOCK) — 박자에 맞추면 판돈과 자원 배율이 오릅니다. 프롤로그 04부터 |
| `Q` | (판) 자세 바꾸기 (STRIKE · STEADY · EXPOSE). 프롤로그 05부터 |
| `P` / `Shift+P` | 저장 / 저장 후 나가기 (걸어 둔 판도 그대로 보관) |
| `R` / `N` | (결과 화면) 재도전(먼저 묻습니다) / 다음 사건 |
| `Esc` | 랭킹과 게시판을 어디서나 닫기 |

아직 열리지 않은 규칙의 키(`E`, `Q`)는 판이 받지 않습니다. NEW GAME+ 회차는 프롤로그 01부터 둘 다 받습니다.
`Ctrl`·`Cmd`·`Alt`를 함께 누른 키는 게임이 받지 않습니다(`Ctrl+R` 새로고침, `Ctrl+P` 인쇄는 브라우저의
것입니다). 글자 키는 자판 배열이 아니라 물리 키(`event.code`)로 읽으므로 한글 자판에서도 같습니다.
`Space`와 `Enter`는 `Tab`으로 옮겨 간 컨트롤이 있으면 그 컨트롤의 것입니다. 판의 결과가 막 정해지는
순간(판정 연출)에는 `저장 후 나가기`가 잠시 거절됩니다. 복원·삭제·로그 비우기·새 게임·재도전처럼 진행을
버리는 동작은 먼저 확인 창을 띄웁니다.

### 편의 설정

첫 화면의 `편의 설정` 서랍에서 고르고, 이 기기에 저장됩니다(`src/state/accessibilitySettings.js`).

| 설정 | 동작 |
|---|---|
| 테이블 시간 1배 / 1.5배 / 2배 | 판의 제한 시계가 그만큼 느리게 흐릅니다. 1배가 아닌 기록은 사건 요약에 `assistTime`으로 남고 랭킹 행에 `테이블 시간 ×1.5`처럼 표시됩니다 |
| 읽기 시계 자동 넘김 끄기 | 브리핑 페이지의 읽기 시계가 멈춘 채로 시작합니다 |
| 번쩍임·흔들림 줄이기 | 붉은 가장자리와 판정 섬광을 약하게, 화면 흔들림과 BUST 섬광을 끕니다 (OS의 동작 줄이기와 별개) |
| 한 글자 단축키 쓰기 | 끄면 숫자와 `W` `E` `Q` `P` `R` `N`이 아무것도 하지 않고, 화면도 그 키를 안내하지 않습니다(카드의 숫자, 결과 화면의 `R`·`N`, 손패 위 안내 줄, `aria-keyshortcuts`). `Space`, `Enter`, `Esc`는 남습니다 (WCAG 2.1.4) |
| 첫 화면 움직임 멈추기 | 흐르는 문구, 움직이는 그림, 깜빡이는 제목을 멈춥니다 (WCAG 2.2.2) |

### 끊어서 하기: 저장과 기기 간 이어하기

쉰다섯 개의 사건을 한 번에 끝내기는 어렵습니다. 그래서 어디서 멈춰도 그 자리에서 이어집니다.

- **판을 걸어 둔 채로 멈추기** — `저장 후 나가기`(`Shift+P`)를 누르거나, 앱을 백그라운드로 보내거나,
  휴대폰이 탭을 정리해도 지금 판(걸어 둔 카드, 밀어 올린 열기, 흐른 시간, 콤보)이 그대로 보관됩니다.
  돌아오면 같은 판이 브리핑 페이지부터 다시 열리고, 판이 열리는 순간부터 남은 시간이 흐릅니다.
  벽의 위치는 저장하지 않고 판의 시드에서 다시 뽑으므로 같은 판에는 늘 같은 벽이 있고, 이미 벽에
  닿아 터진 판은 보관되지 않습니다. 멈췄다 돌아오는 것으로는 BUST를 되돌릴 수 없습니다.
- **기기에 먼저, 온라인은 켰을 때만** — 모든 저장은 이 기기(브라우저 저장소)에 기록됩니다. 온라인 저장은
  **기본으로 꺼져 있고**, 첫 화면의 `다른 기기에서 이어하기` 패널에서 `온라인 저장 사용`을 켠 기기만
  올립니다. 켜면 그때 이어하기 코드가 만들어지고, 이후 저장은 몇 초 뒤 온라인에도 올라갑니다.
  오프라인이면 기기에만 두었다가 연결이 돌아오는 순간 올립니다. 게임은 네트워크를 기다리지 않습니다.
- **올라가는 것과 남는 것** — 온라인에 올라가는 사본에는 분석관 이름, 피드백의 자유 의견, 전송 대기 중인
  텔레메트리가 빠집니다. 다른 기기의 사본을 불러와도 이 기기의 이름, 데이터 제공 동의, 전송 대기열은
  그대로 남습니다.
- **플레이테스트 데이터 제공 동의** — 저장본이 없는 기기에서는 첫 화면 `데이터 저장 안내` 서랍의 체크박스가
  켜진 채로 시작합니다. 한 번 끈 기기는 꺼진 채로 남고, 복구 지점이나 보관본을 되돌려도 지금 이 기기의
  동의가 유지됩니다. 초기화하면 기본값(켜짐)으로 돌아갑니다. 도중에 동의를 켠 회차는 서버가 사건 전부를
  보지 못했으므로 온라인 시즌 랭킹에 오르지 않고, 결과 화면이 그렇게 말합니다.
- **다른 기기에서 이어하기** — 온라인 저장을 켠 기기의 패널에는 이어하기 코드(`XXXX-XXXX-XXXX`)가
  보입니다. 다른 기기에서 그 코드를 입력하면 멈춘 자리부터 이어지고, 이후로는 두 기기가 같은 코드에
  저장합니다. 서버는 더 최근 저장을 오래된 저장으로 덮어쓰지 않으므로, 오프라인으로 오래 있던 기기가
  다른 기기의 진행을 지우지 못하고 대신 "더 최근 저장 불러오기"를 제안합니다.
- **리플레이 링크는 저장하지 않습니다** — 다른 사람이 공유한 장면 재현 링크로 들어오면 그동안 이 기기의
  저장은 전혀 바뀌지 않습니다. 새 판을 시작하거나, 복구 슬롯을 되살리거나, 온라인 사본을 불러오면
  재현 모드가 끝납니다.
- **연결 없이 다시 열기** — 한 번 연결된 상태로 연 기기는 연결이 없어도 게임이 열리고 저장한 자리에서
  이어집니다. 홈 화면에 설치한 사본도 같습니다. 첫 판이 열린 뒤 기기가 한가할 때 남은 사건과 화면을
  미리 받아 두며(브라우저의 데이터 절약 모드에서는 받지 않습니다), 다 받기 전에 연결이 끊기면 아직 못
  받은 화면에서 "연결이 끊겼습니다 · 다시 시도"가 나옵니다. 랭킹, 게시판, 온라인 저장은 연결이 있어야
  합니다. 아래 "오프라인(서비스 워커)" 참고.

### 데이터와 접근성

- 브라우저 자동 저장, 완료 기록 JSON 내보내기, 로컬 랭킹은 서버 없이 동작합니다.
- 일반 저장과 별도로 최근 5개 복구 슬롯을 유지합니다. 슬롯은 장면마다가 아니라 돌아갈 만한 자리에서만
  만듭니다: 판을 시작하거나 이어서 열 때, 사건을 열 때, 사건을 닫을 때, 그리고 에러가 났을 때
  (`shouldCaptureSaveSlot`). 슬롯은 판단 로그 전체를 담습니다. 슬롯이나 보관해 둔 사본을 되살릴 때는 시즌의
  모든 사건을 받은 뒤에 고칩니다(아직 받지 못한 사건의 기록을 "모르는 장면"으로 버리지 않도록). 저장된
  사건과 장면이 어긋나면 해당 사건 시작 장면으로 보정하고 복구 알림을 남깁니다. 저장에 없던 키를
  기본값으로 채우는 것은 보정으로 세지 않으므로, 평범하게 다시 불러온 저장이나 라벨이 하나 늘어난 뒤의
  옛 저장에는 복구 알림이 뜨지 않습니다. 첫 화면은 저장을 고치거나 사건을 직접 시작하지 않고,
  로드맵·NEW GAME+ 선택도 게임 런타임에 넘깁니다.
- 이어할 진행이 있는 기기에서 `첫 케이스 시작`이나 `NEW GAME+ 시작`을 누르면 먼저 묻습니다(복구 지점은
  남습니다). 전체 초기화의 확인 창은 지워지는 것(저장된 진행, 순위 기록, 복구 지점, 오류 기록)과 남는 것(화면과
  소리 설정, 도구 도감, NEW GAME+ 기록, 게시판 이름, 이어하기 코드와 온라인에 올린 저장)을 적어 보여 줍니다.
  세션 기록과 다음 참가자에게 쓰던 말도 함께 지우고, 텔레메트리 세션 id를 새로 받습니다
  (`src/state/runStorageReset.js`).
- 사건 기록과 시즌 기록은 **대기열에 먼저 넣고** 보냅니다. 전송 도중 탭이 닫혀도 다음에 열 때 다시 보냅니다.
  텔레메트리 대기열에서 형식이 깨진 항목은 버리고 저장 자체는 살립니다. 서버가 그 행 자체를 받지 않는다고
  답한 항목(속도 제한이나 "아직 이르다"는 거절을 뺀 4xx)은 재시도하지 않고 대기열에서 뺍니다. 데이터 제공
  동의를 거두면 대기열을 비우고, 그때 전송 중이던 묶음이 실패해도 되살아나지 않습니다.
- 글자 크기는 rem입니다. 브라우저나 기기의 기본 글자 크기를 키우면 화면의 글자도 따라 커지고, 정보를 담은
  라벨은 11px 아래로 내려가지 않습니다.
- 실명, 연락처, 회사명을 감지해 익명화를 돕고, 분석관 이름과 게시판 글 길이를 제한합니다.
- 장면·엔딩·초상화는 WebP로 제공하며 480/960px 변형을 함께 둡니다. 키 비주얼만 `<picture>`와
  `image-set`의 JPEG 대체본을 갖습니다. 휴대폰 폭(700px 이하)은 화소 밀도로, 그보다 넓은 화면은
  화면 폭으로 파일을 고릅니다(`src/responsiveArt.js`): 전체 폭 배경이라 960px 화면까지는 960px
  변형을, 그보다 넓으면 원본(1672px)을 받습니다. `index.html`의 preload가 같은 목록을 씁니다.
- 배경음은 사용자 제스처 이후 장면 분위기에 맞춰 재생됩니다. 결정 창에는 벽까지의 거리로 빨라지는
  심박, 열기로 열리는 드론, 밀 때마다 반음씩 오르는 칩 소리, BUST의 파열음이 붙습니다. 모든 큐는
  `acquireCueRuntime()`에서 음소거와 볼륨을 확인하며, 음소거된 플레이어에게는 `AudioContext`
  자체를 만들지 않습니다. 탭이 가려지면 공유 `AudioContext`를 멈추고, 자동재생 차단을 풀려고 달아 둔
  리스너는 소리가 한 번 켜지면 떼어 냅니다. 모션 줄이기 설정은 화면 흔들림만 끄고, 적색 비네팅과 BUST
  섬광은 남깁니다.
- 지금 누를 수 없는 버튼(`GuardedButton`)도 키보드 초점은 받습니다. 스크린 리더가 그 버튼과 막힌 이유를
  읽을 수 있어야 하기 때문입니다.
- 화면이 바뀌면 초점이 따라갑니다. 게임에서 첫 화면으로 돌아오면 첫 화면의 제목(로드맵으로 돌아왔다면
  로드맵 제목과 지금 사건의 카드)으로, 결말의 각 단계에서는 그 단계의 제목이나 첫 컨트롤로, 마지막에는
  리포트 제목으로 갑니다. 저장 상태는 늘 붙어 있는 한 자리에서 읽어 주고, 데이터 제공 동의의 오류는 체크박스
  옆에 나옵니다. 영어로 된 머리말과 제목에는 `lang="en"`이 붙어 있습니다.

## 검증

```bash
npm run verify:static # 브라우저가 필요 없는 검사 25개, 병렬 (~40초)
npm run verify:quick  # verify:static + 빌드 + 번들 예산 + 빌드 위 런타임 스모크 + @prod e2e
npm run verify        # verify:quick + 기본 e2e + 성능 예산
npm run verify:full   # verify + 전체 경로 검증 + 시즌 연속 걷기
npm run test:visual   # 시각 회귀만 (베이스라인은 리눅스 전용 — 로컬은 test:visual:docker)
```

`verify:static`(`scripts/verify-static.mjs`)은 단위·스모크 테스트, lint(`eslint --cache`), 압박
시뮬레이션, 엔딩, 밸런스, 타입(`check:types`), 대사, 그래프, 런타임 예산, 뷰 계약, 상수, 텍스트, 쉬운 말,
인코딩, CSS 토큰, CSS 구조, CSS 포맷, 아트 예산, 폰트, 내보내기 스키마, 테스트 저장소 키, 시각
베이스라인, Node 핀, DB 권한, 서사 사실(canon) 25개 검사를 한꺼번에 돌리고, 모두 끝난 뒤 실패한 것을 모아 보고합니다.
한 검사가 실패해도 나머지가 가려지지 않습니다. `npm test`도 `node --test`로 돌아가므로 어서션 하나가
실패해도 나머지가 모두 실행되고, `tests/unit/**/*.test.mjs`를 함께 줍니다.

대사를 사건 파일(`src/nodes/*.js` 55개)에서 JSON으로 옮기면 텍스트 검사가 열 배 빨라진다는 안은 재 보고
접었습니다. 아래는 2026-10-09에 이 PC에서 `node`로 스크립트를 직접 돌린 3회 중앙값입니다.

| 검사 | 걸린 시간 |
| --- | --- |
| `check:plain-language` | 681ms |
| `check:dialogue` | 378ms |
| `check:canon` | 2,180ms |
| `check:text` | 808ms |

넷을 더해 4.0초이고, 어느 것도 `verify:static`(55.5초)의 길이를 정하지 않습니다. 그 길이는
`check:pressure`, `check:endings`, 커버리지 실행이 정합니다. 사건 파일 55개를 JS로 불러오는 데 168ms, 같은
데이터를 JSON으로 읽는 데 14ms가 걸리므로 검사 하나가 아낄 수 있는 시간은 많아야 0.15초쯤이고, 이는 실행할
때마다 달라지는 폭 안에 있습니다. 치러야 할 값은 따로 있었습니다. 카드의 대사와 답을 라벨에서 떼어 내야
하고(빌드 코드는 셋을 일부러 한자리에 둡니다. `src/gameData.js`의 `fileLines`와 연결 장면 주석에 까닭이
있습니다), 스캐너 넷과 시각 회귀 job의 경로 필터가 JSON을 읽도록 고쳐야 하며, 줄마다 남는 변경 기록을
잃습니다.

넷 중 느린 것은 `check:canon` 하나였고, 파일마다 세 번 읽는 것이 원인이었습니다. 지금은 파일을 한 번만
줄로 나눠 사실과 날짜를 함께 읽습니다. 같은 날 앞뒤 스크립트를 번갈아 5회씩 잰 중앙값은
1,853ms(1,753~1,918)에서 855ms(810~898)로 내려갔고, 찾아내는 것은 그대로입니다.

`verify:quick`의 브라우저 검사는 개발 서버가 아니라 `dist/`를 `vite preview`로 띄운 프로덕션 빌드(디버그
도구가 빠진, 배포되는 그 빌드)에서 돌고, 러너는 떠 있는 서버가 지금의 `dist/index.html`을 내주는지
확인한 뒤에만 씁니다. 개발 모드 스모크는 `npm run test:runtime:dev`입니다.

기본 e2e는 `@visual`(스크린샷)과 `@season-full`(시즌 연속 걷기)을 뺀 전부입니다. 스펙 파일을 직접 지정해도
`--grep`을 함께 주지 않으면 이 둘은 빠집니다. 시즌은 일곱 사건씩
여덟 구간(`@season-segment`)으로 나눠 걷고, GitHub Actions는 기본 e2e를 샤드 세 개에 나눠 push마다
돌립니다. 끊지 않는 연속 걷기(`npm run test:e2e:season`)와 전체 경로 검증(`npm run test:e2e:full`)은
`Full Coverage` 워크플로가 매주 월요일과 수동 실행으로 수행합니다. 그 워크플로의 마지막 job은 실패한
실행마다 이슈 "Full Coverage is failing"을 열거나 댓글을 달고(예약 실행에서는 시간 초과로 취소된 job도
실패로 셉니다), 기본 브랜치의 실행이 다시 초록이 되면 그 이슈를 닫습니다. 이슈가 보고한 실패보다 오래된
초록 실행(옛 실행 다시 돌리기)은 이슈를 닫지 않습니다. PR에서는 `verify:quick`만 돌고,
e2e는 push·`e2e` 라벨·Dependabot PR에서 돕니다. 시각 회귀는 `main` push, 그림을 바꿀 수 있는 파일(스타일시트·
`index.html`·폰트·모든 `.jsx`·`src/` 바로 아래의 모든 `.js`(`caseCopy.js`·`gameCases.js`·`appCopy.js` 등)·`src/viewModels/`·`src/gauntlet/`·`src/nodes/case01.js`·`case05.js`·`public/`·critical CSS 스크립트·
`vite.config.js`·`playwright.config.js`·`tests/helpers/`·`package-lock.json`·스펙과 베이스라인)을 건드린 PR, `visual` 라벨이 붙은 PR, Dependabot PR, 수동 실행에서 돕니다.

`tests/offline.spec.js`는 서비스 워커를 켜는 단 하나의 스펙입니다. e2e 빌드는 `?sw=1`로 연 페이지에서만
워커를 등록하므로, 나머지 스펙은 워커 없이 빌드를 돌립니다. 이 스펙은 프로덕션 빌드를 한 번 연 뒤 연결을
끊고 다시 열어, 저장한 판이 이어지는지와 받아 두지 못한 화면에서 새로고침 대신 재시도 패널이 나오는지를
봅니다. Playwright WebKit에서는 건너뜁니다(워커와 오프라인 컨텍스트를 함께 돌려 보지 못했습니다).

스펙 파일은 `scripts/run-e2e.mjs`의 목록(기본, 프로덕션 빌드, 주간) 중 하나에 들어 있어야 돕니다.
`npm run check:specs`는 모든 스펙이 로드되는지와 함께, 어느 목록에도 없고 `package.json` 스크립트가
이름으로 부르지도 않는 스펙이 있으면 실패합니다.

WebKit(iPhone 14) 프로젝트는 아직 주간 워크플로에서만 돌고, 두 번에 나눠 돕니다. `npm run
test:e2e:webkit`은 프로덕션 빌드에서 `@prod` 테스트를, `npm run test:e2e:webkit:layout`은 개발 서버에서
`@layout` 측정을 돌립니다(측정은 프로덕션 빌드에 없는 디버그 점프로 장면에 들어갑니다).

워크플로의 액션은 전부 커밋 SHA로 고정하고 옆 주석에 태그를 적습니다. 버전 올리기는 Dependabot(npm과
액션, 매주, 묶어서; 메이저 버전과 `@playwright/test`는 제외 — Playwright는 시각 회귀 컨테이너와 함께
올려야 합니다)이 제안합니다. 프로젝트를 돌리는 job들이 함께 쓰는 준비 단계(Node, `npm ci`, Playwright
브라우저)는 `.github/actions/setup`에 한 번만 적혀 있습니다. 워크플로 권한은 `contents: read`이고, 저장소
내용에 쓰는 것은 기록한 베이스라인을 브랜치로 올리는 job 하나뿐입니다. 이슈에 쓰는 것은 `Full Coverage`와
`Migration Drift`의 보고 job 둘이고, 둘 다 프로젝트 코드를 실행하지 않습니다.

## 생성물

만들어서 저장소에 커밋하는 파일들입니다. 배포 환경에는 Playwright 브라우저가 없으므로 빌드가 이것들을
다시 만들지 않습니다.

- `npm run build:art` — 반응형 이미지 변형. `npm run check:art`가 예산을 지킵니다.
- `npm run build:critical` — 인트로가 실제로 칠하는 CSS. `src/styles/critical.generated.css`에
  쓰고, `vite.config.js`가 이를 인라인한 뒤 전체 스타일시트를 `media="print"`로 내려 비차단으로 받습니다.
  다 받은 스타일시트를 되돌리는 것은 빌드가 따로 내보내는 작은 스크립트(`deferred-styles-*.js`)이고,
  `index.html`에는 인라인 스크립트가 하나도 없습니다(CSP가 막습니다). 생성 파일은 잘라낸 스타일시트의
  해시를 함께 기록하므로, 스타일이 바뀌면 빌드가 재생성을 요구하며 실패합니다.
- `npm run build:fonts` — Pretendard를 게임이 실제로 쓰는 글자만 남겨 자른 폰트 한 벌
  (`src/assets/fonts/pretendard-cp.woff2`, 약 266KB, 글꼴 이름 "Critical Point Sans", 첫 화면이 미리
  받습니다). 폰트 CDN도, 여러 조각으로 나뉜 동적 서브셋도 없습니다. **새 문구를 쓰면 이 명령을 다시
  돌리십시오** — `npm run check:fonts`는 원고에 폰트에 없는 글자가 있으면 실패합니다. `pretendard`
  패키지는 원본 TTF를 주는 개발 의존성일 뿐입니다. 굵기는 900까지만 씁니다. 완성형 2,350자(KS X 1001)를
  통째로 담는 고정 목록으로 바꾸는 안은 재 보고 접었습니다. 2026-10-09 기준 지금 파일은 272,208바이트
  (1,695자, 한글 1,243자)이고, 2,350자를 합치면 461,852바이트(2,803자)로 1.7배가 되어 폰트 예산
  (283,500바이트)을 넘습니다. 첫 화면이 미리 받는 파일이라 그만큼이 첫 방문에 얹힙니다.
- `npm run build:icons` — 앱 아이콘(`public/icons/`)을 제작자 그림 `public/profile.jpg`에서 크기별로
  잘라 만듭니다. 파비콘은 이 그림입니다. `public/manifest.webmanifest`의 테마 색은 `#06090a`.

예산은 내리기만 하고 올리지 않습니다. `npm run check:bundle`은 청크마다의 크기에 더해 **첫 페인트**
전체(HTML, 그것이 거는 스크립트·스타일시트, 미리 받는 폰트, 휴대폰이 고르는 키 비주얼)의 전송 바이트를
재며(지금 약 499KB), 폰트 파일과 서비스 워커(`sw.js`)에도 따로 예산이 있습니다. 인트로 화면은 진입 청크에 들어 있어 따로 받지
않고, 게임 런타임 청크는 브라우저가 한가할 때나 시작 버튼에 포인터·초점이 갈 때 미리 받습니다. 시즌은
사건 하나씩 받습니다. 앱 빌드는 장면 그래프를 빌드 때 Node에서 한 번 만들어(`scripts/vite-season-data.mjs`)
사건마다 청크(gzip 15~20KB, 장면이 서른 개로 가장 많은 사건 01만 24KB)로 내보내므로, 게임 런타임 청크는 약
170KB(gzip)이고 첫 시작은 첫 사건(프롤로그 01) 하나만 기다립니다. 나머지는 첫 판 뒤에서 받습니다. 기다릴
범위는 저장본이 있느냐가 아니라 저장본이 무엇을 담고 있느냐로 정합니다(`src/state/savedRunScope.js`): 첫 사건
밖의 장면을 가리키는 저장본, 읽히지 않는 저장본, 복구 슬롯이나 보관한 사본이 있는 기기, 리플레이 링크는 모든
사건을 받은 뒤 엽니다(그동안 화면은 받은 사건 수와 `다시 불러오기`를 보여 줍니다). 받지 못한 청크가 있으면
연결이 있을 때는 한 번 새로고침하고, 연결이 없을 때는 새로고침하지 않고 재시도 패널을 띄웁니다
(`src/state/chunkReload.js`, `src/components/LazyScreen.jsx`). 계속
움직이는 페인트 속성 애니메이션은 게시판 버튼의 빛(`board-glow`) 하나뿐입니다.

## 배포

Render 배포는 `render.yaml`을 기록으로 둡니다(아래 참고).

- Build: `npm ci --include=dev && npm run build`
- Publish: `dist`

Render 빌드는 검사를 다시 돌리지 않습니다. `Verify`가 초록인 커밋만 배포되기 때문입니다(아래 `Deploy`
워크플로). 빌드는 Render가 넣어 주는 값 두 가지를 읽습니다. `RENDER_GIT_COMMIT`은
`<meta name="build-sha">`로 `index.html`에 적히고, `SITE_URL`(없으면 `RENDER_EXTERNAL_URL`)은
og·canonical 주소를 절대 주소로 만듭니다. 페이지는 `viewport-fit=cover`와 `color-scheme: dark`로
그려집니다.

### 자동 배포

`render.yaml`의 설정은 실제 서비스에 적용되지 않습니다. 그 파일은 Blueprint 명세라서 Render가
Blueprint로 관리하는 서비스에만 적용되고, 대시보드에서 직접 만든 서비스는 대시보드 설정을 따릅니다.
헤더도 마찬가지라 대시보드에 손으로 옮겨 두어야 합니다.

대시보드(서비스 → Settings → Headers)에 있어야 하는 규칙 전부입니다. 값의 원본은 `render.yaml`의
`headers:`이고, 긴 값(CSP, Permissions-Policy)은 거기서 그대로 복사합니다.

| 경로 | 헤더 | 값 |
| --- | --- | --- |
| `/assets/*` | `Cache-Control` | `public, max-age=31536000, immutable` |
| `/*.webp` | `Cache-Control` | `public, max-age=86400, stale-while-revalidate=604800` |
| `/*.jpg` | `Cache-Control` | `public, max-age=86400, stale-while-revalidate=604800` |
| `/icons/*` | `Cache-Control` | `public, max-age=86400, stale-while-revalidate=604800` |
| `/` | `Cache-Control` | `no-cache` |
| `/index.html` | `Cache-Control` | `no-cache` |
| `/sw.js` | `Cache-Control` | `no-cache` |
| `/manifest.webmanifest` | `Content-Type` | `application/manifest+json` |
| `/*` | `X-Content-Type-Options` | `nosniff` |
| `/*` | `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `/*` | `Strict-Transport-Security` | `max-age=63072000; includeSubDomains` |
| `/*` | `Cross-Origin-Opener-Policy` | `same-origin` |
| `/assets/*` | `Cross-Origin-Resource-Policy` | `same-origin` |
| `/*` | `Permissions-Policy` | `render.yaml`의 값 |
| `/*` | `Content-Security-Policy` | `render.yaml`의 값 |

2026-10-06에 더해진 것은 그림 세 줄(`/*.webp`, `/*.jpg`, `/icons/*`)과 `/sw.js`입니다. 이 넷은 대시보드에
넣기 전까지 `check:deploy`가 실패가 아니라 경고로 알립니다. `check:deploy`는 세 그림 규칙마다 페이지가 부르는 파일을
하나씩(`.webp`, `og:image`의 `.jpg`, 아이콘) 읽고, 빠진 규칙마다 경고합니다.

배포를 거는 것은 `.github/workflows/deploy.yml`입니다. Render 대시보드 → 서비스 → Settings → Deploy
Hook에서 URL을 복사해 저장소 시크릿 `RENDER_DEPLOY_HOOK`에 넣으면, `Verify`(e2e 포함)가 초록으로 끝난
`main` 푸시마다 배포를 겁니다. Render의 자체 Auto-Deploy는 CI 결과와 무관하게 배포하므로 꺼 둡니다
(`render.yaml`에도 `autoDeploy: false`로 기록). 훅은 검증된 커밋을 `ref=`로 지정해 부르고, Render는 특정
커밋으로 배포된 서비스의 Auto-Deploy를 스스로 끄며 대시보드에 "Auto-Deploy has been disabled to prevent
accidental deploys"라고 표시합니다. 이것이 의도한 상태이니 다시 켜지 마십시오.
시크릿이 없으면 배포를 걸지 않고 실행에 경고 주석을 남깁니다.

같은 job이 이어서 배포된 사이트를 확인합니다. 저장소 시크릿 `DEPLOY_URL`이 있으면 사이트가 **배포를 건
바로 그 커밋의 `build-sha`를 내줄 때까지 기다린 뒤**(사이트가 이미 그 커밋을 내주고 있었다면 — 킬 스위치나
환경 변수 수정처럼 같은 커밋을 다시 배포한 경우 — 페이지나 `sw.js`가 바뀔 때까지 기다리고, 10분간 안
바뀌면 경고를 남긴 뒤) `npm run check:deploy`로 살아 있는지, 보안 헤더,
캐시 정책, 그리고 진입 스크립트에 CSP의 `connect-src`가 허용한 백엔드 주소가 들어 있는지를 봅니다.
마지막 것은 `VITE_SUPABASE_URL` 없이 빌드된 배포를 잡습니다. 그런 배포는 헤더가 전부 맞는데도 랭킹·
게시판·온라인 저장이 꺼져 있습니다. 루트에서 내려가는 이미지(`public/`의 장면 그림·초상화·키 비주얼)의
캐시 정책은 실패가 아니라 경고로 남깁니다. `render.yaml`은 하루(`max-age=86400`)로 적어 두었지만,
대시보드 Headers에 같은 규칙(`/*.webp`, `/*.jpg`, `/icons/*`)을 손으로 넣기 전까지는 호스트 기본값이
나갑니다. `/sw.js`도 봅니다. 찾은 워커의 릴리스를 말하고, 킬 스위치 워커면 경고하며, 없거나 함께 나간 페이지와
다른 릴리스의 것이면 실패하고, 중간 캐시가 붙잡을
수 있는 헤더로 나가면 경고합니다(대시보드 Headers에 `/sw.js` → `Cache-Control: no-cache`를 넣어야
합니다). 시크릿이 없으면 아무것도 가져오지 않았다는 경고 주석을 남깁니다. 손으로 돌릴 때는:

```powershell
$env:DEPLOY_URL = "https://<서비스-이름>.onrender.com"   # 실제 서비스 주소로 바꿔서
npm run check:deploy
node scripts/check-deploy.mjs --offline   # 네트워크 없이 render.yaml, dist/index.html, dist/sw.js만
```

CSP는 있는지가 아니라 **값으로** 검사합니다(`scripts/deploy-policy.mjs`). `script-src`는 `'self'`뿐이고
`'unsafe-inline'`·`'unsafe-eval'`이나 와일드카드가 있으면 실패하며(`script-src-elem`·`script-src-attr`가
있으면 같은 기준으로 봅니다), `object-src 'none'`이어야 하고, `base-uri`·`frame-ancestors`는 있어야 하며
와일드카드면 실패합니다. `Permissions-Policy`는 `render.yaml`이 끄는 17개 기능이 모두 꺼져 있어야 합니다. `render.yaml`의 값은 `img-src 'self' data: blob:`, `font-src 'self'
data:`, 그리고 `form-action`·`manifest-src`·`worker-src`가 `'self'`입니다. `style-src`만 인라인 critical
CSS와 React의 style 속성 때문에 `'unsafe-inline'`을 남깁니다. 빌드된 `index.html`에 인라인 스크립트나
`on*=` 핸들러가 생기면 오프라인 검사가 잡습니다.

`VITE_SUPABASE_URL`과 `VITE_SUPABASE_ANON_KEY`는 값 없이 선언되어 있으므로 Render 대시보드에서
설정합니다. 없으면 앱은 텔레메트리, 원격 랭킹, 게시판, 온라인 저장을 끈 채로 조용히 동작합니다(배포 뒤
`check:deploy`가 이 경우 실패합니다. 오프라인 검사는 주소가 진입 청크가 아닌 다른 청크에 들어 있으면
실패하고, `render.yaml`에서 15개 규칙 중 하나라도 빠져도 실패합니다). 서비스 롤 키는 Render에도 브라우저에도 넣지 않습니다.

### 오프라인(서비스 워커)

빌드는 `dist/sw.js`를 씁니다(`vite.config.js`의 `serviceWorker()`, 조립은
`scripts/service-worker-build.mjs`, 코드는 `src/serviceWorker/worker.js`). 릴리스 빌드의 페이지가 `load` 뒤에
등록하고(`src/serviceWorker/register.js`), 개발 서버는 등록하지 않습니다.

| 요청 | 워커가 하는 일 |
| --- | --- |
| 페이지(`/`) | 네트워크 먼저. 실패하거나, 3초 동안 답이 없거나, 서버가 오류(400 이상)로 답할 때만 받아 둔 페이지 |
| `/assets/*` (해시가 붙은 파일) | 받아 둔 것 먼저. 없으면 네트워크에서 받아 보관 |
| 루트의 그림·아이콘·매니페스트 | 받아 둔 것을 바로 주고 뒤에서 새로 받음. 연결도 사본도 없으면 같은 그림의 다른 크기 |
| 다른 출처(Supabase), GET이 아닌 요청, `/sw.js` | 손대지 않음 |

- **릴리스 하나에 캐시 하나.** 이름은 `critical-point-<릴리스>`이고, 릴리스는 Render 빌드에서는
  `<커밋>-<페이지가 부르는 파일 이름들의 해시 8자>`, 로컬 빌드에서는 빌드된 `index.html`의 해시입니다. 같은
  커밋을 환경 변수만 바꿔 다시 배포해도 다른 릴리스가 됩니다. 새 워커는 설치되면 바로
  넘겨받고 다른 릴리스의 캐시를 지웁니다.
- **설치 때 받는 것**은 빌드된 페이지가 이름으로 부르는 파일 전부입니다(진입 스크립트·스타일·폰트·아이콘·
  매니페스트·키 비주얼 세 크기). 하나라도 못 받거나 파일 이름으로 HTML이 오면 설치되지 않고, 전부 받은 뒤에
  한꺼번에 보관합니다. 받아 온 페이지가 이 릴리스의 진입
  스크립트를 부르지 않으면(배포가 그 사이에 바뀐 경우) 역시 설치되지 않습니다.
- **나머지**(사건 55개, 지연 화면, 초상화, 960px 그림)는 첫 판이 열린 뒤 페이지가 워커에 요청해 받습니다.
  오프라인이거나 데이터 절약 모드면 요청하지 않고, 중간에 끊기면 연결이 돌아올 때 다시 요청합니다. 새 릴리스의
  워커가 페이지를 넘겨받으면 그 워커에 다시 요청합니다.
- **청크 요청에 페이지를 대신 주지 않습니다.** 배포 뒤에 남은 옛 탭이 사라진 청크를 요청하면 예전처럼
  실패하고, 그 실패가 새로고침으로 이어집니다(`src/state/chunkReload.js`). 열어 둔 탭에서 워커가 새
  릴리스로 바뀐 뒤 오프라인이 되면, 패널은 "다시 시도" 대신 "새로고침"을 내놓습니다(받아 둔 새 버전이
  열립니다).
- **끄는 법(킬 스위치).** Render 대시보드의 환경 변수에 `SERVICE_WORKER=off`를 넣고 배포하면, 페이지는
  워커를 등록하지 않고 `sw.js`는 자기 캐시를 지우고 스스로 등록을 해제하는 워커가 됩니다. 이미 워커가
  있는 기기는 다음 방문 때 그 파일을 받아 워커가 사라집니다. 변수를 지우고 다시 배포하면 돌아옵니다. 이 배포는
  같은 커밋의 재배포이므로 Deploy는 `sw.js`가 바뀔 때까지 기다리고, `check:deploy`가 "The service worker is
  switched off" 경고를 남깁니다. 변수를 지우지 않으면 이후 모든 배포에 이 경고가 붙습니다.
  로컬에서는 `SERVICE_WORKER=off npm run build`.
- **Render 대시보드에 손으로 넣을 것.** Settings → Headers에 `/sw.js` → `Cache-Control: no-cache`.
  `render.yaml`에 적혀 있지만 그 파일은 실제 서비스에 적용되지 않습니다(위 "자동 배포"). 브라우저는
  워커 파일을 받을 때 자기 HTTP 캐시를 건너뛰므로 이 규칙이 없어도 동작은 하고, 중간 캐시가 옛 파일을
  몇 분 붙잡을 수 있을 뿐입니다. `check:deploy`가 경고로 알려 줍니다.
- **확인하지 못한 것.** iOS Safari와 홈 화면에 설치한 사본에서는 돌려 보지 못했습니다. 자동 검사는
  Chromium(데스크톱·모바일 뷰포트)뿐입니다.

### 수동 배포와 롤백

자동 경로는 되돌리지 않습니다. 사이트가 이미 더 새 커밋을 내주고 있으면 옛 커밋의 `Verify`가 다시
끝나도 배포를 걸지 않습니다. 되돌리거나 같은 커밋을 다시 배포하려면 `Deploy` 워크플로를 손으로
실행합니다.

```bash
git log --oneline --first-parent main        # 되돌아갈 커밋(병합 커밋)을 고릅니다
gh workflow run Deploy --ref main -f sha=$(git rev-parse <커밋>)
gh run watch                                  # 사이트가 그 커밋을 내주는지까지 확인합니다
```

- `sha`는 40자 전체 해시입니다. 비워 두면 실행한 ref의 머리 커밋입니다.
- 손으로 건 배포도 자동 경로와 같은 관문을 지납니다. 커밋이 `main`에 있어야 하고, 그 커밋의 **push로 돈
  `Verify`가 초록**이어야 합니다. 병합된 브랜치 중간의 커밋은 그런 실행이 없으므로 병합 커밋을 지정합니다.
  관문에 걸리면 실행이 빨갛게 끝나고 아무것도 배포되지 않습니다.
- 관문을 건너뛰려면 `-f force=true`를 더합니다. 실행에 경고 주석이 남습니다. `Verify`가 고장 나 있어서
  그것을 기다릴 수 없는 때에만 씁니다.
- 되돌린 뒤에는 `main`도 되돌려야 합니다(`git revert`로 새 커밋을 만들어 push). 그러지 않으면 다음 push의
  `Verify`가 초록이 되는 순간 문제의 커밋이 다시 배포됩니다.
- 되돌리는 커밋이 마이그레이션보다 앞선 것이면 스키마는 그대로 남습니다. 마이그레이션은 되돌리는 파일을
  새로 써서 `main`에 병합합니다(병합이 곧 적용입니다. 아래 원격 랭킹 3번).

## 원격 랭킹 (선택)

1. `.env.example`을 `.env.local`로 복사하고 `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`를 채웁니다.
2. 스키마는 마이그레이션 파일로만 바꿉니다. 마이그레이션은 `supabase/migrations/`에 있고, 원격 이력이
   유일한 출처입니다. 대시보드 SQL 에디터로 직접 적용하지 마십시오. 손으로 적용해야 할 때는
   `npx supabase link --project-ref <ref>` 후 `npx supabase db push`를 씁니다. `supabase` CLI는 개발
   의존성으로 버전이 고정되어 있어 `npx supabase`가 그것을 씁니다.
3. **`main`에 병합하면 마이그레이션이 곧바로 운영 데이터베이스에 적용됩니다.** Supabase의 GitHub 연동이
   켜져 있고(대시보드 → Project Settings → Integrations → GitHub, Deploy to production, production
   branch `main`), 병합 커밋에 "Supabase Preview" 체크로 결과가 남습니다. 2026-10-06 병합에서는 1분 안에
   적용됐습니다. 클라이언트는 그 뒤 `Verify`와 `Deploy`를 거쳐 15분쯤 늦게 바뀝니다. 그래서 **순서는
   데이터베이스가 먼저**이고, 그 사이에는 옛 클라이언트가 새 스키마를 만납니다.
   - 한도나 권한만 바꾸는 마이그레이션은 클라이언트 변경과 한 PR로 병합해도 됩니다.
   - 서버가 받는 행이나 공개 컬럼의 모양을 바꾸는 마이그레이션(2026-09-28의 것들이 그랬습니다)은 옛
     클라이언트가 쓰거나 읽다가 거절당합니다. 새 모양과 옛 모양을 둘 다 받는 클라이언트를 **먼저 다른
     PR로 병합해 배포를 확인한 뒤**, 마이그레이션을 따로 병합합니다.
4. 익명 사용자는 테이블 전체 권한을 하나도 갖지 않습니다. 마이그레이션이 `anon`·`authenticated`의
   권한을 모두 거둔 뒤 필요한 컬럼만 다시 줍니다. 쓰기는 텔레메트리 세 테이블과 게시판의 정해진 컬럼
   insert뿐이고, 읽기는 `playtest_sessions`의 `run_tag`, `player_name`, `case_id`, `case_title`,
   `completed_at`, `summary`, `score`와 게시판의 `id`, `nickname`, `body`, `created_at`뿐입니다. RLS가
   점수가 있는 시즌 완주 행만 보이게 하고, `public_rankings` 뷰는 `security_invoker = true`로 같은
   규칙을 상속해 서버가 계산한 `score` 순으로 줍니다. `run_id`와 `session_code`는 공개되지 않습니다.
   `npm run check:grants`는 테이블 단위 권한이 하나라도 있으면 실패하고, 클라이언트가 실제로 보내는
   요청을 익명 역할로 그대로 실행해 봅니다. `search_path`를 고정하지 않은 `SECURITY DEFINER` 함수와
   `security_invoker`가 없는 뷰도 실패입니다.
5. 시간과 모양은 서버가 정합니다. `created_at`·`completed_at`은 클라이언트가 무엇을 보내든 `now()`이고,
   행과 필드마다 크기 상한이 있으며, 랭킹 이름은 늘 `익명 분석관`입니다. 시즌 기록은 그 런이
   `season_case_ids()`의 모든 사건 행을 이미 남겼고 첫 사건 행이 10분 이상 지났을 때만 받고, 런마다 한 줄,
   세션마다 하루 두 줄까지입니다. **사건을 더하거나 빼면 `season_case_ids()`를 다시 정의하는
   마이그레이션도 필요합니다** — `check:grants`가 `CASE_SEQUENCE`와 다르면 실패합니다.
6. 요청 제한의 주소는 `request_client_ip()`가 정합니다. `cf-connecting-ip`가 있으면 그것, 없으면
   `x-forwarded-for`의 가장 오른쪽(신뢰하는 프록시가 붙인) 주소입니다. 카운터는 원자적으로 올리는
   `bump_rate_limit`이 셉니다. 텔레메트리는 (주소, 세션)마다 시간당 240건, 주소마다 1,200건이고, 바이트로는
   주소마다 하루 32MB(`telemetry_address_daily_bytes`), 모두 합쳐 하루 200MB(`telemetry_daily_bytes`)
   입니다. 괄호 안은 `private_settings`의 이름으로, 마이그레이션 없이 바꿀 수 있습니다. 주소 한도가 전체
   한도보다 먼저 닿으므로 한 주소가 다른 플레이어의 하루치를 다 쓰지 못합니다.
7. 텔레메트리 행은 만들어질 때 한 번 받은 `event_id`(`src/state/telemetryEventId.js`)를 재시도에도 그대로
   씁니다. `event_id`는 유니크이고, 클라이언트는 평범한 POST를 보내 유니크 위반(`409`, 코드 `23505`)만 전달 완료로
   셉니다(`on_conflict`는 `event_id`에 대한 SELECT 권한이 필요해서 쓰지 않습니다). 다른 이유의 `409`는 실패입니다. 피드백 행은
   `{ event_id, session_id, session_code, case_id, feedback: { caseTitle, submittedAt, clarity,
   difficulty, comment } }` 모양이고, 자유 의견(`comment`)은 피드백 행에만 허용됩니다. 첫 전송 전에
   개인정보 검사를 거칩니다.
8. 기기 간 이어하기는 `cloud_saves` 테이블을 씁니다. 익명 사용자는 이 테이블을 직접 읽거나 쓸 수 없고,
   `put_cloud_save`, `get_cloud_save`, `peek_cloud_save`, `delete_cloud_save` 네 함수로만 한 코드의 한 행에
   접근합니다. 행은 코드의 SHA-256으로 저장되고, `saved_at`은 `now()`를 넘지 못하며, 기기 사이의 순서는
   서버의 `revision`으로 정합니다(시각이 아님). 충돌은 플레이어가 고를 때까지 유지되고, 패널에서 서버 사본을
   지울 수 있으며(`delete_cloud_save`), 마지막 업로드 후 180일이 지나면 만료됩니다. 쓰기는 코드마다 시간당 240번·주소마다 600번, 읽기는
   주소마다 시간당 120번까지입니다. 새 코드는 주소마다 하루 5개, 모두 합쳐 하루 1,000개(`cloud_daily_new_codes`)까지
   만들 수 있고, 넘으면 새 코드만 거절되고 이미 있는 코드의 저장은 계속됩니다.
9. `free_text_analyses` 테이블은 기록으로만 남아 있고 서비스 롤만 접근합니다. 게임은 여기에 쓰지 않습니다.

공개 플레이테스트가 아니라면 전용 프로젝트를 쓰고 키를 주기적으로 교체하십시오. 스테이징은 별도
Supabase 프로젝트를 쓰고, 운영 마이그레이션 전에는 `npx supabase migration list --linked`와
`npx supabase db push --dry-run`으로 먼저 확인합니다.

클라이언트는 `Verify`가 초록이면 저절로 배포되고, 마이그레이션은 병합 때 Supabase 연동이 적용합니다.
연동이 꺼지거나 적용에 실패하면 저장소와 데이터베이스가 어긋난 채로 남습니다. 둘이 어긋났는지는 `Migration Drift` 워크플로(`.github/workflows/migration-drift.yml`)가 하루에 한 번
봅니다. 운영 프로젝트의 마이그레이션 이력을 `supabase migration list`로 받아 `supabase/migrations/`와
양쪽으로 비교하고(`scripts/check-migration-drift.mjs`), 저장소에만 있는 파일이나 데이터베이스에만 있는
버전이 있으면 실행이 빨갛게 끝나며 이슈 "Supabase migrations are out of step"을 열거나 댓글을 답니다.
다시 맞으면 그 이슈를 닫습니다. 예약 실행이 10분 제한에 걸려 취소되면 "물어보지 못함"으로 이슈에 남기고,
14자리가 아닌 원격 버전은 "데이터베이스에만 있음"으로 보고하며, CLI 출력은 자격 증명을 가려서 로그에만
남깁니다. 병합 때 연동이 적용하므로 이슈가 열렸다면 적용이 실패했거나 연동이
꺼진 것입니다. 병합 커밋의 "Supabase Preview" 체크를 보고, 손으로 `db push`한 뒤 첫 실행에서 닫힙니다.

이 워크플로는 저장소 시크릿 `SUPABASE_ACCESS_TOKEN`이 있어야 일합니다. 없으면 아무것도 묻지 않았다는
경고 주석만 남기고 초록으로 끝납니다. 토큰은 supabase.com → 계정(Account) → Access Tokens에서
만들고(개인 액세스 토큰, 이름은 자유), 값을 복사해 다음처럼 넣습니다.

```bash
gh secret set SUPABASE_ACCESS_TOKEN          # 프롬프트에 토큰을 붙여 넣습니다
gh workflow run "Migration Drift"            # 바로 한 번 돌려 봅니다
```

토큰 권한은 좁게 줍니다. **대상은 이 프로젝트 하나, 권한은 데이터베이스 읽기와 쓰기**면 됩니다
(2026-10-06에 그 토큰으로 돌려 확인). 읽기만 준 토큰은 "Initialising login role..."에서 실패합니다. CLI가
이력을 읽기 전에 데이터베이스에 임시 접속 역할을 만들기 때문입니다. 모든 권한을 준 토큰도 동작하지만
그 계정의 모든 프로젝트를 다룰 수 있으니 쓰지 않습니다. 어느 쪽이든 이 시크릿 말고는 어디에도 적지
않습니다. 데이터베이스 비밀번호(`SUPABASE_DB_PASSWORD`)는 필요 없었습니다. 목록 단계가 실패하면 CLI가
한 말이 그 단계의 로그에 남습니다(자격 증명처럼 보이는 값은 가려서). 손으로 볼 때는
`npx supabase link --project-ref <ref>` 뒤에:

```bash
npx supabase migration list --linked --output-format json > list.json
node scripts/check-migration-drift.mjs --from list.json
```

텔레메트리 보관 기간은 `public.purge_old_telemetry(interval)`이 관리합니다. 텔레메트리 세 테이블,
게시판, `free_text_analyses`, 오래된 온라인 저장, 요청 제한 카운터까지 일곱 테이블을 비우고, 30일보다
짧은 기간은 거부하며 기본값은 180일입니다. `pg_cron`이 있는 프로젝트에서는 마이그레이션이 매일 한 번
실행하도록 예약하고, `anon`·`authenticated`에는 권한을 주지 않습니다.

`db push` 뒤에 손으로 확인할 것:

- 요청 제한 주소가 맞는지 — `cf-connecting-ip`를 직접 넣어 보낸 요청이 다른 주소로 세어지지 않는지.
- `pg_cron`에 `purge-old-telemetry` 작업이 생겼는지(확장이 없으면 마이그레이션은 예약을 건너뜁니다).
- Render 대시보드의 CSP가 `render.yaml`의 값과 같은지.
- Supabase 대시보드에서 회원가입이 꺼져 있는지(`supabase/config.toml`은 로컬 설정일 뿐입니다).
- 공개 랭킹이 비워졌는지 — 새 규칙을 통과하지 못하는 시즌 기록은 이 마이그레이션이 지웁니다.

원격 저장을 설정하지 않아도 플레이, 자동 저장, JSON 내보내기, 로컬 랭킹은 그대로 동작합니다.

## 개발 메모

- 개발 도구는 Vite 개발 모드에서 `?debug=1`을 붙이거나 `VITE_ENABLE_DEBUG_TOOLS=true`일 때만
  노출됩니다. 디버그 패널에서 복구 슬롯 복원·삭제, 기록된 사건/장면으로 바로 재현 진입,
  `playtest_sessions`·`playtest_feedback`·`app_error_logs` 읽기 점검을 할 수 있습니다.
  운영 RLS에서 anon 키를 insert 전용으로 두면 저장은 되어도 헬스체크는 `확인 필요`로 뜹니다.
- 에러가 나면 현재 저장본을 `paused`로 남기고 로컬 에러 로그를 기록합니다. 원격 전송은 데이터
  제공 동의가 있는 저장본에서만 하며, 대기열은 온라인 복귀 후 지수 백오프로 재시도합니다.
- 결과 화면의 기본 공유 요약은 `src/state/playtestExport.js`가 조립하며, `playerName`, `log`,
  `sessionId`, `errorLog`, `saveSlots`, `trace`가 빠지는지 단위 테스트로 고정합니다. 원문은
  디버그 진단 로그에만 들어갑니다.
- Windows PowerShell은 유효한 UTF-8 한글을 깨져 보이게 출력할 수 있습니다. 화면에서 깨져 보인다는
  이유로 원고를 고치기 전에 `npm run check:encoding`과 `npm run check:text`를 기준으로 삼으십시오.
- Prettier는 `src/styles`만 관리합니다(`npm run format`). `app.css`가 다시 압축된 형태로
  커밋되는 것을 막기 위한 장치이고, JS/JSX 포맷은 diff 가독성을 위해 강제하지 않습니다.
- ESLint(`npm run lint`)에서 `no-unused-vars`와 `no-undef`는 오류, `react-hooks/exhaustive-deps`와
  `react-hooks/set-state-in-effect`는 경고입니다. 후자는 `AppContent`가 아직 명령형으로 다루는
  효과들에 대한 남은 과제입니다.
- 사건 하나는 파일 하나입니다. 쉰다섯 사건 모두 `src/nodes/*.js`가 그 사건의 장면과 표(여파·연결·반응
  장면, 효과와 대사, 샛길, 숨은 라우트, 단서 반전, 오프닝, 장면 좌표, 결말 표)를 한 객체로 내보내고,
  `src/nodes/casePacks.js`에 올리면 각 표를 가진 모듈이 합칩니다(사건 01~11과 마지막 사건은 옛 표에서 그대로
  옮겨 와 모양이 조금 느슨합니다). 손으로 적는 것은 사건 순서와 시작 장면
  (`src/gameCases.js`), 예고·막간·챕터 규칙(`src/caseCopy.js`), 음악 모티프, 그리고 서버의
  `season_case_ids()`를 다시 정의하는 마이그레이션입니다. 장면의 `next`는 적었다면 조립된 그래프가
  실제로 쓰는 값이어야 하고(`check:graph`), 새 문구를 썼다면 `npm run build:fonts`를 다시 돌립니다.
- 카드 하나는 `{ id, label, effect, voice, echo, cognition }` 객체 하나입니다. 연결·반응 장면의 카드는 인지
  유형을 적지 않으면 라벨 문구에서 읽습니다(`inferChoiceCognition`). 이 추론은 부정문("빼지 않고")과 명사 속
  낱말("제안서")을 가리지 못하므로, 틀리게 읽히는 카드에는 `cognition`을 직접 적습니다(지금 90장).
  `check:graph`는 직접 적은 값이 한 가지 유형(재구성은 2, 나머지는 1)인지를 보고, 단위 테스트
  (`tests/unit/sceneBuild.test.mjs`)는 라벨이 이미 그렇게 읽히는 카드에 중복으로 적지 않았는지를 봅니다. 라벨을 고쳐 추론을 유도하지 마십시오. 인지 유형은 결말 판정에 들어갑니다.
- 관계·적응 카드처럼 런타임이 사건의 닫는 장면에 붙이는 카드는 그 장면의 **대표 카드**(`leadChoiceId`)를
  따라가고, 사건 결과도 대표 카드로 기록합니다(`src/seasonRules.js`). `check:graph`가 이를 지킵니다.
- 판의 상태는 한 표에서 나옵니다. `src/state/runState.js`의 `RUN_FIELDS`가 필드마다 저장 키, 새 값, 그리고
  새 게임·사건 열기·장면 점프·초기화에서 지울지 남길지를 적고, 화면의 상태와 저장본에 쓰는 내용이 같은 줄에서
  만들어집니다(`runTransition`, `toSavePayload`). 판을 시작하고 여는 동작은 `src/state/runLifecycle.js`에
  있습니다. 저장 필드를 더하려면 그 표에 한 줄을 더합니다.
- `npm run raise:gains`는 모든 카드의 이득 수치를 10% 올리는 스크립트입니다. 인자 없이 돌리면 바뀔 것을
  보여 주기만 하고, `--write`를 주어야 파일을 고칩니다(작업 트리가 깨끗할 때만). 돌린 뒤에는
  `npm run check:endings`를 읽어야 합니다.
